Markov Chains

Oracle B needs a weather model the agent could plausibly know in advance — not "here is what actually happened," but "here is how likely each condition is to follow the current one." A Markov chain is exactly that model, fit from nothing more than counting.

The same idea page 2 of the Phase 1 prerequisites already taught you

An MDP's Markov property says the next state depends only on the current state, not on the full history of how you got there — that's what made laps_remaining, not cumulative_race_time_so_far, the right state feature back in Phase 1. A Markov chain is the same idea, stripped of actions and rewards entirely: just a set of states and the probability of moving from each one to each other one at each step. Weather regime is a natural fit — tomorrow's conditions depend mostly on today's, not on the conditions three days ago — which is exactly the assumption Oracle B's weather model makes explicit and calibrates.

The transition matrix

With n states, a Markov chain is completely described by an n × n transition matrix P, where each entry is a conditional probability:

P[i, j] = P(next state = j | current state = i)

Every row of P must sum to 1 — from state i, the chain has to go somewhere at the next step, possibly back to i itself. A matrix with this property is called row-stochastic. For this project, n = 3: DRY, DAMP, WET.

Fitting a chain from data: count, then normalize

Given a log of observed weather sequences, the transition matrix that makes those exact sequences most probable (its maximum-likelihood estimate) has a famously simple closed form: count how many times each transition i → j actually occurred, then divide by how many times state i occurred as a starting point at all:

n_ij = number of observed transitions from state i to state j n_i = Σ_j n_ij (total number of times state i was the starting point of a transition) P̂[i, j] = n_ij / n_i

No optimization, no iteration — just counting and dividing. This is the standard estimator for a Markov chain's transition probabilities, and it falls directly out of maximizing the likelihood of the observed sequences under a Markov-chain model (a classical result, e.g. Anderson & Goodman 1957). One practical edge case worth knowing before it surprises you: a state that was never observed as a starting point has n_i = 0, making the division undefined — the standard fix is to fall back to a uniform row (equal probability to every state) rather than leaving that row undefined or crashing on it.

Worked example: fitting a 3×3 matrix from three toy races

Three short, invented 6-lap weather logs (D = DRY, P = DAMP, W = WET), one letter per lap:

Race 1: D D D P P D Race 2: D D P W W P Race 3: D P P D D D

Read off every consecutive pair within each race (never across race boundaries — race 1's last lap says nothing about race 2's first) and tally them by starting state:

From→ D→ P→ WRow total (n_i)
D5308
P2215
W0112

Every row sums to 1, as required. Notice what the matrix quietly encodes just from three short races: DRY is "sticky" (62.5% chance of staying DRY), WET never jumped straight back to DRY in this small sample (a real fit, with far more than three races of data, would likely assign that transition a small but nonzero probability rather than exactly zero — a reminder that a fitted chain is only as good as the data behind it, a point Oracle B's fit-quality reporting takes seriously; see below).

Sampling a trace from a fitted chain

To generate a new, synthetic weather trace lap by lap: start in some initial state, then at each step draw the next state from the current row of P̂, treated as a probability distribution over the three states — a single random draw weighted by that row's three numbers, then move to whichever state was drawn and repeat using its row next. Two traces sampled this way, even starting identically, will almost always diverge after a few laps, precisely because each step re-samples the randomness fresh — the same "no memorisable answer key" property page 1 flagged as the reason safety cars can't just be replayed from history.

Worth knowing, not needed for this project

Multiplying the matrix by itself, P², gives two-step transition probabilities; P^k gives k-step ones. As k grows large, most well-behaved chains converge to a fixed stationary distribution — the long-run fraction of time spent in each state, independent of where the chain started. The oracle never needs this (races are short and the exact lap-by-lap distribution is what backward induction consumes, not a long-run average), but it's the concept you'll see if you read further about Markov chains anywhere else.

Why this is what makes Oracle B "achievable" and Oracle A only a "bound"

This is the piece that makes the two-oracle design in the Phase 3.5 plan precise rather than hand-wavy:

  • Oracle A conditions the backward induction on one specific, fixed historical weather trace — lap 12 really was DAMP in that particular real race, and Oracle A is allowed to know that in advance while solving. No RL agent, which only observes weather up to the current lap, could ever know that. Oracle A is provably an upper bound the agent cannot reach — not because the agent isn't good enough, but because it's being asked a harder question than the agent is ever asked.
  • Oracle B instead conditions on the fitted transition matrix above, tracking weather_regime as part of the DP state exactly the way the live environment does, and computing the expectation over next-lap weather using P̂'s row for the current regime — precisely the mechanism page 3 introduced for the safety car, applied to a second, independent random process. Because the agent, too, only ever observes the current regime and has to reason probabilistically about what comes next, Oracle B is solving exactly the MDP the agent actually faces. Its value is a target the agent could, in principle, actually reach.
  • The gap between them — Oracle A − Oracle B — is the value of knowing the future in advance: a genuinely interesting number in its own right, not RL underperformance. Page 6 returns to this with the real project's numbers.
This project

weather_markov.py fits one 3×3 matrix like the one above per circuit, from every historical race template Phase 0.5 extracted for that circuit — the exact counting-and-normalizing procedure above, just with far more than three races and far more than six laps behind it. It also reports fit quality (per-transition counts, held-out likelihood): if a circuit's historical sample is too thin for the fitted chain to be trustworthy, the honest response is to say so and lean on Oracle A's information-gap framing instead of quietly presenting a poorly-fit Oracle B as the tight benchmark.

sb3_wrapper.py as a direct instantiation of page 06, with page 07's findings applied

make_masked_env wraps a single F1StrategyEnv with ActionMasker, exposing the environment's existing action_masks() method (Phase 1, assumed background) in the format page 06's MaskablePPO expects. make_vec_masked_envs is where page 07's findings land. The lambda in ActionMasker(env, lambda e: e.action_masks()) is not a bug inside SB3, which ships environment factories with cloudpickle, but a module-level def _mask_fn(env): return env.action_masks() is still the better habit. The choice that matters is the vector class: DummyVecEnv is the recommended one for this environment, about 14 times faster than SubprocVecEnv on a step this cheap (measured in lab p9-07) and with no worker processes to start. If SubprocVecEnv is kept, the training script needs an if __name__ == "__main__": guard, or under Windows's spawn every worker re-runs it on import.

ppo_agent.py's eval-mode asymmetry, and Finding D

PPOAgent.select_action calls self.model.predict(obs, action_masks=masks, deterministic=True) — page 06's .predict() in its deterministic mode. This already does the right thing by construction. Contrast this directly against Finding D (assumed background from the eval-mode fix already required of Phase 4/5's agents): QLearningAgent and DuelingDoubleDQNAgent both still branch on self.epsilon at evaluation time, meaning roughly 5% of their "trained" actions during evaluation are still uniformly random — including occasional random pit stops. The real plan's own Risks table names this exact asymmetry. PPO's evaluation code does not need fixing; the custom DQN/Q-learning agents do, and that fix must land before this phase's comparison numbers mean anything, independent of page 08's training-budget fix.

The gamma: 1.0 row is the one place J3 (the audit's third Phase 9 finding) enters this set, and it is a cross-reference rather than new content: with γ = 1.0 and uncentred rewards, PPO's value head faces the same ≈ −5,000 target problem DQN already had (Finding C, assumed background from the Phase 4/5 sets). The fix is the same one already taught there — reward_offset: "base_pace" — and it applies here unchanged; nothing about PPO's own math (pages 01–04) requires revisiting it. Measured on the toy race (the p9-cap report): MaskablePPO found the exact optimum in 1,000 races with the reward centred, and with the raw reward ended 38.48 s away on every seed, the gap of a network that has learned nothing. Here the fix is not a speed-up; without it PPO does not learn.

Page 09 / 10 — Reading guide, not reproduction

Code Walkthrough

A reading order for src/agents/q_learning_agent.py, src/agents/train_tabular.py, and configs/q_learning.yaml — what to look for and why, not a copy of the code itself.

Reading order, and why it's this order

Read discretize_obs first, before either agent class — it's the representation everything else depends on, and page 8 already walked through it dimension by dimension. Then read QLearningAgent: select_action, update, save/load, in that order, since update only makes sense once you've seen how an action gets chosen in the first place. Only after that, read SARSAAgent as a subclass — it overrides exactly two methods, and reading it last means every line that isn't overridden is already familiar.

What to look for in QLearningAgent

  • select_action — confirm it matches page 3's ε-greedy shape exactly: a random draw restricted to np.where(masks)[0] (the legal actions), or an argmax over self.Q[state] with illegal actions set to −inf first. The state key passed in is always the output of discretize_obs, never the raw observation.
  • update — this is page 2's update rule, line for line: target = reward if terminated, else reward + gamma * np.max(next_q) with the next state's illegal actions masked to −inf first, exactly the max_a' from page 2. Confirm the masking happens before the max, not after — an unmasked max could pick an illegal action's stale Q-value as the target, which would be wrong for the same reason unmasked exploration wastes budget on page 3.
  • save / load — the Q-table is a defaultdict at training time (so unvisited states cost nothing, page 5's arithmetic), but pickling a defaultdict with a lambda default factory doesn't round-trip cleanly through every serialization path — check that load reconstructs the defaultdict wrapper explicitly around the loaded plain dict, rather than assuming pickle preserved it.

What to look for in SARSAAgent.select_action's pre-commit mechanic

This is page 7 stage 4's _pending_action mechanism, under its real name, _next_action. The reason it exists at all: SARSA's update needs to know a' — the action the agent will actually take next — before it can compute this step's TD target, but Gymnasium's env.step() loop naturally hands back next_obs before the loop asks for the next action. select_action resolves this by checking for a pre-committed _next_action first (consuming and clearing it if present) and only falling back to a fresh ε-greedy draw otherwise; update is where that pre-commit actually gets set, by calling select_action on next_obs one call early. If page 7 stage 6's leak exercise was done first, this pattern — and the exact way it can go stale across an episode boundary if never reset — should already look familiar rather than surprising.

The training loop's curriculum switch and evaluation cadence

In train_tabular.py, look for the options["curriculum_dry_only"] = True branch, set for episode < curriculum_episodes and passed straight through to env.reset(seed=episode, options=options) — this is page 8's two-switch curriculum, and the environment side of honoring that flag lives in Phase 1's code, not here. Then look at the periodic evaluation block, printed every eval_interval episodes: this is what makes a learning curve trustworthy rather than a single lucky checkpoint. A single evaluation run at the very end of training could land on an unusually easy or unusually hard batch of seeds and give a misleading impression of how training actually progressed; periodic in-training evaluation, checked against the smoothed episode_rewards[-100:] average printed alongside it, is what lets a reviewer distinguish steady genuine improvement from a noisy fluke near the end.

What each new test actually catches

In the same spirit as Phase 3.5 page 7's test-by-test walkthrough — read what each test is actually defending against, not just that it exists:

TestWhat it actually catches
test_q_learning_update_changes_q_valuesThe single most basic thing that could silently break: an update call that's a no-op, e.g. because the learning rate never gets applied or the wrong cell gets written. Doesn't check the update is correct, only that it does something.
test_epsilon_decaysThat the decay schedule from page 3 actually decreases epsilon over repeated steps, and respects the floor — not a check on the exact decay curve, just that decay is genuinely happening rather than being silently skipped (e.g. because _step never gets incremented).
test_trained_q_agent_beats_randomAn end-to-end sanity floor, deliberately weak: after only 1,000 training episodes (far short of the real 10,000-episode run), the agent should at least beat an agent that acts uniformly at random. This is a smoke test that the whole pipeline — environment, discretization, update rule, exploration — is wired together correctly, not a claim that the agent has learned good strategy. A model that narrowly fails this test almost certainly has a wiring bug somewhere upstream, not a hyperparameter problem; one that passes it says nothing yet about how it compares to the threshold baseline, let alone the Oracle B optimality gap that's the phase's actual headline metric.

Also worth checking against page 6's audit finding: confirm a test exists (or add one) asserting discretize_obs maps the Phase 3.5 DP oracle's optimal pit lap, and its immediate neighboring laps, to distinct table keys — without it, none of the three tests above can catch the case where the whole training pipeline runs cleanly, reports a plausible-looking learning curve, and is still structurally incapable of representing the optimal policy.

Six Ways the Plan's Pseudocode Breaks Its Own Race

Page 05 was a missing rule. These are ordinary-looking bugs in the code around it, each a mistake worth recognizing anywhere.

Your call · a rival counted twice

In the plan's code, a rival's lap time is added to its total inside RivalState.advance_lap, and then again in the environment's step(). On the Pit Wall's race the rival's true time is 231.37 s.

What does the bug do to the race?

E1: rival lap times counted twice

RivalState.advance_lap ends with self.total_time += lap_time, and F1MultiCarEnv.step() adds the same lap time again for every rival. Two pieces of code, written at different times, both believe they own one update. The effect looks like a learning curve succeeding: an agent racing crippled rivals beats all of them from its first untrained race. That is why the Definition of Done asks for a test that each total grows by one lap's time per lap.

E2: the pass that gets overwritten

When attempt_overtake succeeds, the plan lowers self._agent_position by one. Two lines later _update_positions() recomputes every position from total time, which the pass never changed, and the decrement is gone. The pattern is a partial update followed by a from-scratch recompute of the same quantity in the same step: each half looks right, and the bug is in their order. The fix is for a pass to change time, as the Pit Wall's engine does, and for order to be read off time alone.

E3: dirty air in the score, not in the race

_compute_reward subtracts dirty_air from the reward, but dirty_air is never added to agent_lap_time. It never reaches the total, the gap or the position. The agent is scored for a pace loss its own lap time says never happened. Wherever the reward and the dynamics disagree, the quickest way to raise the reward is to work the gap between them: a surface for reward hacking, not a cosmetic slip. Putting the wake in the lap time, where −lap_time picks it up, closes it.

The numbers sayAbout 463 s, behind every time

The rival's total grows by two laps' time per lap, so it finishes in about 2 × 231.37 = 462.74 s. Your worst one-stop is under 270 s. You finish ahead in every race, with any plan.

So the place bonus becomes 20 s added to every plan alike, and no rival script can change who finishes ahead. E1 doesn't cause the case, but it would hide it: every reward curve looks like a win.

E5: a theorem's name on a flat bonus

The plan's reward_type="potential_shaping" branch computes:

return base_reward - dirty_air + (1/n_total if pos_norm < 1.0 else 0)

A flat bonus for not being last, paid every lap whether the position improved or not. No Φ is stored, no difference is taken, and page 03's theorem says nothing about it. The fix: store self._prev_potential in reset() and at the end of each step(), add γ·Φ(s′) − Φ(s) with Φ(s) = −position_normalized, and set Φ(s′) = 0 on the final step. Naming code after a theorem doesn't make the theorem apply; the guarantee attaches to the form.

How the ledger hides the case

The plan as written is the blocking-off race three ways over: no holding-up line (page 05, E4 in the audit), passes that never stick (E2), and a wake that never touches the lap time (E3). Fix any one alone and the other two still keep position free. E1 then makes the agent win every race, so nothing in the training curves would look wrong.

Evidence so farThree faults each keep track position free: the missing holding-up line, the overwritten pass (E2) and the wake left out of the lap time (E3).

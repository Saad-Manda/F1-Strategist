Lambdas, Processes, and the Guard Windows Needs

An audit finding, tested on this machine. It points at the wrong line; the right line is one most people forget.

Your call · the plan's lambda

The plan builds each environment with ActionMasker(env, lambda e: e.action_masks()) and runs four of them in SubprocVecEnv. On Windows, workers start by spawn: a fresh Python that receives everything it needs as bytes. Plain pickle refuses lambdas.

What happens when the plan's code runs?

Functions across a process boundary

Processes don't share memory, so a worker can only receive “how to build this environment” as bytes. Plain pickle stores a module-level function by name (“import this module, look up this name”); a lambda has no importable name, so pickle raises PicklingError. The audit's finding J1 says the plan's lambda fails this way on Windows, while Linux hides it by forking.

SB3 doesn't use plain pickle for environment factories. It wraps each in CloudpickleWrapper, and cloudpickle serialises lambdas by value. The plan's factory, lambda and all, built four workers and trained MaskablePPO under spawn. Linux isn't hiding anything either: SB3 defaults to forkserver there, not fork.

A claim about what breaks across a process boundary depends on which serialiser and which start method are in use. A three-line script answers it faster than reading; lab p9-07 runs three.

What does break: the guard

Under spawn every worker is a fresh interpreter that re-imports the script you ran. If that script builds the SubprocVecEnv at the top level, every worker reaches the same line while importing and tries to start workers of its own. Python stops it with a RuntimeError (“An attempt has been made to start a new process before the current process has finished its bootstrapping phase”), or the run hangs. The fix lives in the training script, the module that is run:

def main(): venv = make_vec_masked_envs(...) MaskablePPO("MlpPolicy", venv, ...).learn(...) if __name__ == "__main__": main()

Still worth doing: a named module-level _mask_fn(env) instead of the lambda, which also works with plain pickle and any tool less forgiving than cloudpickle.

The better answer for this race: DummyVecEnv

One step of this environment is a handful of arithmetic, so shipping actions and observations between processes costs more than the work. Measured with four copies of a comparably cheap environment: 41,468 steps a second in DummyVecEnv against 3,010 in SubprocVecEnv, about 14 times faster, before the 3 to 6 seconds SubprocVecEnv takes to start its workers. Nothing crosses a process boundary, and no guard is needed.

Evidence so farNot this: the case's run doesn't crash, and the plan's lambda wouldn't stop one. The real J1 is a missing __main__ guard, and DummyVecEnv avoids it while running 14 times faster. Next: what the plan's comparison would conclude.

Lambdas, Processes, and the Guard Windows Needs

A general lesson about functions crossing a process boundary, then what actually happens to the plan's code on this machine, measured. The audit's finding turns out to point at the wrong line.

The general lesson

SubprocVecEnv (page 06) has to get "how to build this environment" into each of its worker processes. Separate processes do not share memory, so the only way to hand one a function is to serialize it: turn it into bytes, send them, and rebuild the function on the other side. Python's standard pickle serializes a module-level function by name, storing only "import this module, look up this name". A lambda or a closure has no importable name, so plain pickle refuses it with a PicklingError. That part of the lesson is true, and the lab measures it.

What the audit claimed

The real plan's make_vec_masked_envs contains:

masked_env = ActionMasker(env, lambda e: e.action_masks())

Audit finding J1 says this lambda cannot cross into the SubprocVecEnv workers, so the line raises PicklingError on Windows, while Linux hides the bug because its fork start method copies the parent's memory.

What actually happens

Measured on this machine

The plan's code runs. Stable-Baselines3 does not use plain pickle for environment factories: it wraps each one in a CloudpickleWrapper, and cloudpickle serializes lambdas and closures by value, code and captured variables included. The plan's exact factory, lambda and all, built four SubprocVecEnv workers and trained MaskablePPO under spawn. The Linux half of the story is off too: SB3 defaults to forkserver there, not fork, so Linux does not hide anything.

The start method does matter, for a different reason. Under spawn, the only method Windows has, each worker is a fresh Python interpreter that re-imports the main module, the script you ran. If that script creates the SubprocVecEnv at the top level, every worker reaches the same line while importing it and tries to start workers of its own. Python stops this with a RuntimeError ("An attempt has been made to start a new process before the current process has finished its bootstrapping phase"); in some setups the run hangs instead. The fix is the standard one:

def main():
    venv = make_vec_masked_envs(...)
    model = MaskablePPO("MlpPolicy", venv, ...)
    model.learn(...)

if __name__ == "__main__":
    main()

That guard belongs in the training script, the module that is run. Nothing inside sb3_wrapper.py can add it.

Still worth doing: a named mask function

The lambda is harmless inside SB3, but a module-level function is the better habit, because it also works with plain multiprocessing, with pickle, and with any tool that is not as forgiving as cloudpickle:

def _mask_fn(env) -> np.ndarray:
    return env.action_masks()

masked_env = ActionMasker(env, _mask_fn)

The lesson generalizes. A claim about what breaks across a process boundary depends on which serializer and which start method are actually in use, and both are details of the library. Here a short script answers it faster than reading about it, which is what lab p9-07 does: three claims, each run in a fresh process with spawn forced.

The better option for this environment: DummyVecEnv

The plan's own Risks table names a fallback worth taking seriously. One F1StrategyEnv.step() is a handful of arithmetic operations, so the cost of sending each step's actions and observations between processes can exceed the work being parallelised. DummyVecEnv runs every copy in one process: nothing crosses a boundary, no guard is needed, and it is faster. Measured with four copies of a comparable cheap environment: 41,468 steps per second with DummyVecEnv against 3,010 with SubprocVecEnv, about 14 times faster, before counting the 3 to 6 seconds each SubprocVecEnv takes to start its workers. Page 06's general trade-off, settled for this environment.

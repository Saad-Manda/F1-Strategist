The settings, in one run's arithmetic

One planned run is 5,000 races of 52 laps, 260,000 steps. With train_freq = 4 that is about 64,750 updates of a batch of 64, so each of the 260,000 transitions is trained on about 16 times. tau = 0.005 closes half a gap in 139 updates, about 11 races (page 03). buffer_size = 100,000 is full by race 1,923 (page 04). ε falls from 1.0 to 0.05 over 200,000 steps, reaching the floor at race 3,846, and the last 1,154 races train at 0.05. lr = 0.001 is page 02's, gamma = 1.0 Phase 1's and max_norm = 10 page 08's.

Two things the arithmetic turns up

β never gets near 1. The buffer raises β one tick per sample() over a 500,000-tick schedule, and the run calls sample() about 64,750 times, so β ends at 0.4 + 0.6 × 64,750 / 500,000 ≈ 0.48. Page 07's full correction late in training never happens; beta_steps should be about the number of updates. The PER settings aren't in the config. alpha and the three β values are missing from configs/dqn.yaml, and the agent builds its buffer with a capacity only, so the buffer's defaults apply. The head width of 64 and max_norm are hardcoded the same way. Neither finding is in the plan's Risks table or the audit.

Issues on record

  • The evaluated agent still explores. The case; the cold open above.
  • The exponent applied twice. add() reads the largest leaf, already p^α, and raises it to α again (page 07). Store the largest leaf as it is.
  • One counter, two owners. self._step is increased only inside decay_epsilon(), and update() reads it to decide whether this is a fourth step. A loop that skips decay_epsilon(), as an evaluation loop reasonably would, makes update() fire every call or never. Count steps in one place both are documented to depend on.
  • Unseeded randomness. select_action and the buffer's sample() draw from NumPy's global state. Paired-seed comparison needs a seeded generator the agent owns, as page 09's learner has.
Deep diveThe files, in reading order340 words

Read DuelingDQN.forward first, five lines whose output shape everything else consumes; then PrioritizedReplayBuffer, which never touches a network; then DuelingDoubleDQNAgent, which joins them; train_dqn.py last.

  • DuelingDQN: three nn.Sequential blocks, the table above. In the combining line the mean must be over the last dimension, across calls, with keepdim=True. A mean over the batch dimension runs without error and subtracts the same six numbers from every row, which does nothing for identifiability.
  • PrioritizedReplayBuffer: _tree_update and _retrieve are page 07's climb and walk, converting indices by capacity − 1. add holds the double exponent. sample uses self.size as N, divides by the batch's largest weight, and advances β one tick per call. update_priorities applies α once, the pattern add should match. Each stored transition carries next_masks (page 06).
  • The agent's constructor copies the online weights into the target with load_state_dict and gives the optimizer only the online parameters: "θ⁻ never receives a gradient". It also accepts target_update_freq, a hard-update setting, and never uses it; only the soft update exists.
  • select_action: ε-greedy with a network, a random legal call or a masked argmax, and no way to switch exploration off.
  • update: a gate (learning_starts and _step % train_freq); inside torch.no_grad(), the online network on the next observations, illegal calls to −inf, an argmax, the target network, a gather, and reward + gamma * value * (1 − done); then a per-row smooth_l1_loss times the weights before the mean, clipping between backward() and step(), priorities written back, and the soft update.
  • save/load store both networks, the optimizer, ε and the step counter, but not the buffer: a resumed run waits for learning_starts again.
  • train_dqn.py: per lap, select_action, env.step, the next state's mask, store, update, decay_epsilon. It logs reward, mean loss, ε and pit count per race. Its docstring promises "Q-value distributions (detect overestimation)" and the loop never logs a Q-value, the one number page 08's symptoms table needs.

What the tests catch

  • test_dqn_target_network_differs_from_online: the target network being the online one, or copied every step. As written it stores 200 transitions under the default learning_starts of 1,000, so update() returns without training and the networks stay identical: it fails for a reason unrelated to what it tests. It also sets agent._step by hand, the counter coupling showing up in a test.
  • test_per_samples_high_td_more: a buffer that stores priorities and samples uniformly anyway. It passes explicit priorities, so the double exponent passes it untouched.
  • test_action_masking_in_exploitation: an illegal greedy call. It covers the choice only, not the mask inside update()'s target.

None of the three would notice exploration at evaluation.

Case 4 · the verdict

The champion was right; the evaluation rolled dice

Why does a champion make stops its own network rates worse? Because the evaluation still explores. With ε = 0.05 the champion makes a random call on one lap in twenty; half of those change its call, and 0.47 a race are pit stops it would never make, in 37.8% of races. Its strategy is 0.28 s from the optimum and its report says 1.94 s. Every suspect inside the network and its training was cleared: its numbers favour staying out at each unplanned stop by seconds, its scale is within 3% of the truth, and a real network fault, seed 0's lap-16 stop, shows at one state in every race.

What should the plan change? The prerequisites don't edit the plan; these go to whoever implements Phase 5.

1. Evaluate greedy, by construction. Give select_action a greedy or eval_mode switch, have evaluate.py set it, and test that two evaluations on one seed give the same race. In the real race the leak is 2.6 random calls a race, some of them 18 s stops. Phase 4's table learner has the same leak (1.89 s on the toy race), so fix it once, in the evaluation code every agent goes through.

2. Fix the memory's two settings faults. Store a new transition at the largest leaf as it is, not raised to α again, and test that path with no explicit priority. Set beta_steps to about the run's 64,750 updates, and put alpha and the β settings in configs/dqn.yaml.

3. Make the tests test what they name. Set learning_starts below 200 in the target-network test. Add four: a new leaf equals the largest existing leaf; a terminal transition's target equals its reward; a target whose next state has one legal call is built from that call; and two evaluations on one seed match.

Also for the implementer: count steps in one place for both update() and decay_epsilon(); give the agent and buffer a seeded generator; log the average Q-value the docstring promises; drop the unused target_update_freq.

Deep diveThe four-way comparison140 words

The phase's headline extends Phase 4's table with one row, all four on the same 100 seeds with paired confidence intervals: the DP oracle (the optimum, 100% of the gap closed), the threshold baseline (0%, by definition), tabular Q-learning, and Dueling Double DQN, each measured. The plan is explicit about one result that would otherwise look like failure: this state space is small, a table with fine enough bins can represent the answer, and if DQN only matches it here, that is a finding to report with the gap numbers. The network earns its place in Phase 6, where rival gaps add continuous dimensions a table can't absorb. The capstone report found the same on the toy race: the table learner 2.2 s off on average after 5,000 races, the networks within a fraction of a second after 600.

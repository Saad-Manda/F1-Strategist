The Binning Bug: When Coarseness Erases the Decision

A binning scheme that runs without error and produces a plausible-sized table is not the same thing as a binning scheme that can represent the optimal policy. This page exists because the real plan's first draft got this wrong, and the fix has to land in discretize_obs before anything else in Phase 4 can be trusted.

Audit finding, quoted directly from the real plan

phase-4-q-learning-sarsa.md flags its own Step 1: "The binning below is too coarse to represent the decision... The agent is structurally prevented from representing the optimum, and no amount of training fixes that." This page exists to make sure that warning is understood before discretize_obs gets written, not discovered afterward from a confusing learning curve.

The concrete numbers

The real plan's tire_age dimension gets 10 bins over a normalization capped at 50 laps of tire age — one bin per 5 laps:

tire_age_bin = min( int(normalized_age × 10), 9 ) # normalized_age = age / 50 bin 0: ages 0–5 bin 1: ages 5–10 bin 2: ages 10–15 ... bin 5: ages 25–30 bin 6: ages 30–35 ...

Why that's fatal, connected directly to Phase 3.5's own numbers

This isn't an abstract concern — it can be checked directly against numbers this project has already validated. Phase 0.5's non-degeneracy check requires the 1-second-optimal pit window (the range of laps within one second of the exact optimal pit lap, as computed by the Phase 3.5 DP oracle) to be ≤12 laps wide, and the Phase 0 audit actually measured windows of 5–10 laps. A 5-lap-wide tire_age bin is frequently narrower than the entire optimal window is wide — meaning two laps the oracle considers meaningfully different can land in the very same table cell.

Concretely: suppose the DP oracle's exact optimal pit lap for some scenario is lap 27, with the 1-second-optimal window running from roughly lap 25 to lap 32 (an 8-lap window, well within the measured 5–10 lap range). Consider two candidate pit laps inside that window, lap 27 and lap 31, both close to optimal but four laps apart:

tire age at lap 27 ≈ 27 → normalized ≈ 0.54 → int(0.54 × 10) = 5 → bin 5 tire age at lap 31 ≈ 31 → normalized ≈ 0.62 → int(0.62 × 10) = 6 → bin 6

Those two happen to land in adjacent bins here — but shift the same window four laps earlier (optimal lap 23, candidates lap 23 and lap 27) and both fall inside bin 4 (ages 20–25) and bin 5 (ages 25–30) respectively only by luck of where the window sits relative to a bin edge; shift it by two laps instead of four (candidates lap 27 and lap 29, both well inside a typical 5–10 lap window) and both round into the same bin 5 (ages 25–30). The table then has no cell in which "pit now" and "wait 2–4 more laps" are different entries — Q(state_with_bin5, PIT) is a single number that has to simultaneously represent the value of pitting at lap 27 and the value of pitting at lap 29, even though the DP oracle can tell these apart and the real cost of picking wrong is real seconds of race time.

This is not underfitting. More training episodes, a better learning rate, a longer epsilon decay — none of it helps, because the representation itself has a ceiling: two states that are genuinely different, with genuinely different optimal actions, are mapped to the same dictionary key before the agent ever sees them. No update rule can recover information the state representation already discarded.

The fix the real plan adopts

Use 1–2 lap resolution on tire_age (25–50 bins), non-uniform if convenient — fine-grained near the cliff, where the decision is genuinely sensitive to a lap or two either way, coarser far from it, where nothing close to the boundary is at stake and a wider bin costs nothing in decision quality.

The natural objection is that finer binning means a bigger table, but page 5 already computed the actual cost: even the deliberately coarse original scheme comes to roughly 172,800 states (or 518,400, per the discrepancy flagged there — either way, single-digit-to-double-digit megabytes as a float64 table). Widening tire_age from 10 bins to, say, 40 bins multiplies the total by 4×, landing well under 100 MB either way — and because self.Q is a defaultdict (page 8), memory is only ever allocated for states that are actually visited during training, not for the full enumerated space. The aggressive coarseness was never buying back meaningful memory savings; it was only costing the ability to represent the optimum.

The general lesson

Echoing Phase 3.5 page 5's own discipline — a clean pipeline isn't a validated pipeline — a binning scheme that runs without error and produces a plausible-sized table is not the same thing as a binning scheme that can represent the optimal policy. The two properties are independent: a scheme can be perfectly bug-free, produce a sensible-looking state count, train without crashing, and still be structurally incapable of distinguishing the decisions that matter.

The concrete test this motivates

discretize_obs must map the Phase 3.5 DP oracle's optimal pit lap, and its immediate neighboring laps, to distinct bins. If it doesn't, Phase 4 isn't measuring the algorithm's ability to learn a good policy — it's measuring the discretization's inability to represent one, and the optimality gap it eventually reports against Oracle B is meaningless regardless of how well Q-learning or SARSA converges on top of it. This test belongs early in tests/test_agents.py, run before any learning-curve result is trusted, in the same spirit as Phase 3.5's test_oracle_no_absurd_exploit sanity check.

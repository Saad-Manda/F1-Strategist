Planning vs. Learning

Phase 4 will estimate a good policy from thousands of simulated races. Phase 3.5 computes the optimal one directly, from the model alone, without playing a single episode to learn from.

Two ways to solve an MDP

Page 1 of the Phase 1 prerequisites established the RL loop: an agent observes a state, acts, receives a reward, and repeats — learning, over many such interactions, which actions tend to pay off. That framing quietly assumes the agent does not know the transition function or reward function in advance; it has to find out by trying things and observing what happens. Every algorithm downstream of Phase 1 in this project's plan — Q-learning, SARSA, DQN, PPO — is built around that assumption. They are all model-free methods: they never see P(s'|s,a) written down anywhere. They infer good behaviour from samples.

But this project's MDP isn't actually unknown. dynamics.py is the transition function, in closed form, and the reward is simply -lap_time. Nothing about how a lap plays out is hidden from the person who wrote the simulator. When the model is fully known like this, a different family of methods becomes available: planning — compute the optimal policy directly from the model, with no trial and error, no exploration, and no sampling error. Dynamic programming is the classic planning method, and it's what Phase 3.5 builds.

Because Phase 3.5's oracle uses the exact same dynamics.compute_lap_time function the live environment and every learning agent train against, its answer isn't a competing model of the world — it's the provably best possible play within the world the agents already live in. That's what makes "optimality gap" a meaningful number rather than a comparison between two different simulators.

Why "exact" is possible here at all

Solving an MDP exactly by exhaustively considering every state is, in general, hopeless — most interesting MDPs have astronomically large or continuous state spaces (imagine trying to enumerate every possible pixel-frame of an Atari game). Exact solving is a size argument, not a different kind of intelligence: it works exactly when the number of distinct situations the agent can be in is small enough to fit in memory and iterate over in reasonable time.

This project's single-car race state is unusually small for a reason worth naming explicitly: every feature in it was chosen, back in Phase 1, to be a compact, discretizable summary — lap number, which of five compounds is fitted, tyre age in laps, a three-bit used-compound mask, whether a safety car is active, which of three weather regimes is in effect. None of that is an accident of convenience; it's the direct payoff of Phase 1's insistence on a minimal, disciplined state (page 2 of the Phase 1 prerequisites' "sufficient statistic" argument). A state design bloated with continuous, high-precision features would have made this phase impossible.

This project

Multiplying out lap × compound × tyre_age × used_mask × sc_active × weather gives roughly 55 × 5 × 55 × 8 × 2 × 3 ≈ 363,000 states, times 6 actions. A modern laptop can fill a value table of that size, for every lap of a race, in well under a second using NumPy array operations — page 2 works through exactly why. Most of those 363,000 combinations are actually unreachable (a tyre can't be older than the number of laps run so far, and the used-mask is implied by which compounds could plausibly have been fitted) — a reachability pass typically cuts the real work by another 5–10×.

What planning buys that learning can't

The headline reason this phase exists is evaluation. "My RL agent beat the rule-based baseline I also wrote" is a comparison against a strawman of your own construction — the baseline's weaknesses are exactly the weaknesses you happened to think of. "My RL agent came within 0.4 seconds of the provably optimal strategy, and here's exactly where the remaining time is lost" is a claim about the ceiling of the problem itself, independent of anyone's cleverness in writing rules.

There's a second, quieter benefit: an exact solver is also the strongest possible test of the simulator. If backward induction — which cannot make a mistake, only report the true optimum of the model as written — discovers a policy that saves an implausible amount of time, that isn't a strategic insight. It's a bug in dynamics.py, found before an RL agent spent three days learning to exploit it and getting blamed for "not really understanding strategy." Page 6 returns to this as the single highest-value test in the whole DP oracle test suite.

One discipline to hold onto now

The oracle computes an answer; it must never teach one. Training an RL agent to imitate the DP policy's actions is a legitimate technique in its own right (imitation learning), but it is a different project from what Phases 4, 5, and 9 are trying to demonstrate — that an agent can discover good strategy from experience, without being shown the answer first. The oracle's role for the rest of this project is strictly evaluator, never teacher.

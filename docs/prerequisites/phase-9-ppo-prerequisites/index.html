Phase 9 PPO Prerequisites

Everything — and only what — you need to build the MaskablePPO training and DQN-comparison work described in phase-9-ppo-sb3.md, assuming you already have the Phase 1, Phase 3.5, Phase 4, Phase 5, Phase 6, and Phase 8 prerequisite sets and nothing more.

This whole phase is a build-vs-buy demonstration

Every earlier learning phase built its algorithm from scratch — a tabular Q-table (Phase 4), then a neural net approximating one (Phase 5) — because those update rules are small, easy to unit-test, and fail loudly when wrong. Phase 9 deliberately does the opposite: it trains PPO through stable-baselines3/sb3-contrib rather than hand-rolling it. Page 05 works through exactly why that's the correct engineering call for PPO specifically, not a shortcut taken because PPO is "too hard" — the point of this phase is to be able to explain that judgment call in an interview, not just to produce a trained model.

Why this phase is different from everything before it

Every phase through Phase 8 learned a value function — a Q-table, then a neural net approximating one — and acted greedily with respect to it. Phase 9 is the first time this project learns a policy directly: a function straight from state to action probabilities, with no Q-values anywhere in the acting agent's decision, only in a separate critic used purely to reduce the training signal's noise. That's a genuinely different algorithm family, not an extension of DQN, and it comes with its own derivation chain (policy gradients → actor-critic → advantage → PPO's clip) that this set builds up from scratch before ever touching the library that actually trains it.

Scope, precisely

This set teaches exactly what phase-9-ppo-sb3.md needs: the policy-gradient idea from first principles through actor-critic, the advantage function, and Generalized Advantage Estimation (GAE-λ — what Stable-Baselines3 actually computes, which idea.md's own concept list omits), PPO's clipped surrogate objective, why PPO specifically is a build-vs-buy case in a way DQN wasn't, Stable-Baselines3/sb3-contrib's API surface generically before it's instantiated as the real sb3_wrapper.py/ppo_agent.py, and two audit findings taught as core lessons: a Windows-fatal SubprocVecEnv + lambda pickling bug, and a "same timesteps ≠ same experience" unfair-comparison bug in the DQN-vs-PPO protocol. It does not preview anything beyond Phase 9 — there is nothing later in the roadmap to preview.

Phase 8 is assumed background, but not load-bearing here

The real plan's own scheduling note says to do Phase 9 before Phase 8 if both stretch phases are attempted — Phase 9 is architecturally independent of self-play. Nothing from PettingZoo, checkpoint pools, or multi-agent training is used below; Phase 8's set is assumed already read only because the user has read it, not because anything here depends on it.

Read this before anything else

Like Phase 6 and Phase 8's sets were for their own phases, this one is unusual: src/agents/ppo_agent.py, src/env/sb3_wrapper.py, and configs/ppo.yaml don't exist in src/ yet, because Phase 9 hasn't been implemented. Pages 10–11 read the plan's own pseudocode, not a real, running file. Pages 06 and 09 also partly describe an external library's documented behavior (stable-baselines3, sb3-contrib) rather than anything to audit for bugs in this repo.

How to use this alongside the Phase 9 plan

Read pages 1–8 once, in order — they build one continuous derivation, from why a policy can be optimized directly at all, through the variance problem and its fix, the specific advantage estimator SB3 actually uses, and the clip that makes reusing a batch of experience across multiple epochs safe — followed by the case for using a library at all, that library's own API shape, and two bugs a careful read of the real plan turns up before any training run wastes a GPU-day on them. Page 9 is hands-on: build a tiny REINFORCE-then-PPO loop yourself, on a toy problem small enough to reason about by hand, including reproducing the pickling bug on purpose. Page 10 then re-derives the same concepts using nothing but this project's actual classes and parameters. Page 11 is a critical reading guide to the plan's own pseudocode. Keep page 12 open as a reference while you work.

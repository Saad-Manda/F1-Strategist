Page 06 / 11 — Six lessons in the shape of ordinary bugs

Six Ways the Plan's Own Pseudocode Breaks Its Own Physics

Page 05 was a missing model. These are six ordinary-looking bugs in the code around it — each one a specific instance of a mistake worth being able to recognize anywhere.

E1 — Rival lap times are double-counted

RivalState.advance_lap already ends with self.total_time += lap_time. The plan's F1MultiCarEnv.step() then loops over every rival and adds the same lap time a second time. Every rival accumulates roughly double its true race time and finishes near-last, every single race.

The general lesson: two different pieces of code, written at different points in the plan, both believing they own the update to the same piece of state. This is an ordinary class of mistake — but here its effect (rivals always finish last) looks exactly like a learning curve succeeding. An agent evaluated against permanently-crippled rivals will "beat" all of them from the very first untrained episode, and a rising reward curve on top of that tells the developer nothing true about whether strategy is being learned. This is precisely why the real plan's Definition of Done asks for a specific regression test on exact-once accumulation, rather than trusting "rivals finish at realistic times" to catch it by eye.

E2 — The overtake result gets silently overwritten

When attempt_overtake succeeds, the plan decrements self._agent_position by one. Two lines later, _update_positions() recomputes every position from scratch from cumulative time — discarding that decrement, since the underlying total_time values never changed.

The general lesson: a stateful, partial update to a quantity, immediately followed by a from-scratch recomputation of that same quantity in the same step, where the recomputation silently wins. This pattern — update, then unconditionally recompute — is worth recognizing on sight as a place bugs like to hide, because both halves individually look correct in isolation; the bug only exists in their sequencing.

E3 — Dirty air is charged to the reward but not the dynamics

Even once page 05's blocking fix is in place, the plan's _compute_reward separately subtracts dirty_air from the reward — but dirty_air is never added to agent_lap_time, so it never reaches _agent_total_time, never affects position, and never affects gaps.

The load-bearing lesson of this page

The agent is penalized in its reward for a pace loss that its own recorded lap time says never happened. Whenever a reward disagrees with what the dynamics actually did, the fastest way for a learning agent to raise its reward is to exploit the gap between what it's scored on and what actually moves it through the environment — that gap is a reward-hacking surface, not a cosmetic inconsistency. docs/idea.md's "common pitfalls" section names exactly this shape of failure as the single most common RL debugging trap on this entire project: a rising learning curve isn't proof of anything by itself, because the agent may be exploiting a flaw in the reward function rather than learning good strategy. Page 05's fix (adding dirty air to the lap time itself, so -lap_time picks it up automatically) is what closes this specific instance of the gap.

E5 — A principled label on an unprincipled implementation

Directly following from page 03. The plan's reward_type="potential_shaping" branch computes:

return base_reward - dirty_air + (1/n_total if pos_norm < 1.0 else 0)

That is a flat bonus for not being in last place — a constant, awarded regardless of whether position improved, worsened, or stayed the same this lap. It stores no Φ(s) from the previous step and computes no difference. Page 03's theorem — that potential-based shaping provably cannot change the optimal policy — says nothing whatsoever about this reward, because this reward is not potential-based shaping in the sense the theorem covers. It's ad-hoc shaping (page 03's own opening example, a flat bonus unrelated to any state-only potential difference) shipping under the theorem's name.

The fix: store self._prev_potential in reset() and at the end of each step(), and compute the actual difference F = γ·Φ(s') − Φ(s) with Φ(s) = -position_normalized, exactly as page 03 worked through.

The general lesson: naming a piece of code after a theorem doesn't make the theorem's guarantee apply to it. The guarantee attaches to the specific mathematical form, not the variable or branch name — worth checking that an implementation actually matches the form a cited result depends on, rather than trusting a comment or a config string that claims it does.

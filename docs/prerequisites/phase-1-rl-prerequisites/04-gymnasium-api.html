The Gymnasium API

The literal interface f1_strategy_env.py must implement — and the one nearly the whole RL ecosystem writes against.

Gymnasium (the maintained successor to OpenAI's original gym library) is the standard interface almost the entire RL ecosystem writes against. If your environment implements Gymnasium's contract correctly, every algorithm library that supports Gymnasium works with it automatically, with no per-algorithm integration code. Phase 1's whole job is to implement this contract for the F1 race MDP.

The Env class and its two core methods

class MyEnv(gym.Env):
    def reset(self, seed=None, options=None) -> tuple[obs, info]:
        """Start a new episode. Returns the first observation."""

    def step(self, action) -> tuple[obs, reward, terminated, truncated, info]:
        """Advance one step. Apply the action, return what happened."""

reset() is called once at the start of every episode — it re-randomizes whatever needs re-randomizing and returns the starting observation. step() is called once per timestep thereafter and returns exactly five things:

  • obs — the new observation after the action.
  • reward — the scalar reward for this step.
  • terminated — True if the episode ended because the task genuinely finished.
  • truncated — True if the episode ended for an external reason unrelated to the task's own logic (e.g. a step-count limit). Gymnasium deliberately splits this from terminated because algorithms compute returns differently for the two: a truncated episode still has value beyond its last step; a terminated one, by definition, does not.
  • info — a free-form dictionary for anything else worth returning that doesn't belong in the observation.
This project

reset() samples a new weather scenario and a new safety-car trace, and returns lap 1's observation. step() computes the lap time for the action taken, applies pit loss if the agent pitted, updates tyre state, and returns the next lap's observation. terminated becomes True exactly when current_lap > total_laps. truncated is always False — Phase 1 deliberately has no external time limit; a race episode only ends when the race itself ends.

Spaces: describing what observations and actions look like

Gymnasium requires every environment to declare, up front, the shape and bounds of its observations and actions — this is what lets a generic algorithm library build a neural network with the right input/output sizes without knowing anything else about your environment.

  • spaces.Box(low, high, shape, dtype) — a (possibly multi-dimensional) array of continuous values within given bounds. Used for observations.
  • spaces.Discrete(n) — one of n distinct integer choices, 0 through n-1. Used for actions.
This project

The observation space is Box(low=0.0, high=1.0, shape=(16,)) — every one of the 16 features is normalized into [0, 1] on purpose. This uniform scaling matters in practice: neural networks train far more reliably when every input feature is on a comparable scale, rather than one feature ranging in the hundreds while another ranges in single digits. The action space is Discrete(6) — the six choices STAY_OUT through PIT_WET.

A standard example: GridWorld, built piece by piece

Everything above is easiest to trust once you've seen it in a working example — and the example this page uses, GridWorldEnv, is a deliberately generic one: an agent moving around a small grid toward a goal. It has nothing to do with F1, tyres, or lap times. That's the point — the Gymnasium contract is a general-purpose interface, and seeing it hold up for a completely different kind of problem is what makes clear which parts of the contract are universal (every custom environment needs them) versus which parts are specific to racing (covered starting page 5). GridWorld is also the closest thing RL teaching has to a "hello world" for writing a custom gym.Env from scratch.

The setup: a 5×5 grid, rows and columns numbered 0–4. The agent starts at the top-left corner (0, 0) and must reach the goal at the bottom-right corner (4, 4). Four actions — up, down, left, right — move it one cell at a time. Build it up one piece at a time, rather than all at once.

First, the constants and the class shell. Nothing but the action labels and the spaces Gymnasium needs declared:

import numpy as np
import gymnasium as gym
from gymnasium import spaces

UP, DOWN, LEFT, RIGHT = 0, 1, 2, 3
GRID_SIZE = 5
MAX_STEPS = 50          # gives truncation something to do -- see below

class GridWorldEnv(gym.Env):
    metadata = {"render_modes": ["human"]}

    def __init__(self):
        super().__init__()
        # obs = [row_normalized, col_normalized], both in [0, 1]
        self.observation_space = spaces.Box(low=0.0, high=1.0, shape=(2,), dtype=np.float32)
        self.action_space = spaces.Discrete(4)   # UP | DOWN | LEFT | RIGHT

Two design choices worth pausing on, because both generalize directly to the real project. First, the observation is normalized to [0, 1] rather than left as raw grid coordinates 0..4 — the same reason page 6 gives for the real environment's 16-dim vector: it keeps every input feature on a comparable scale, which matters once a neural network is reading it. Second, the position is encoded as two continuous numbers rather than one Discrete(25) state — a modelling choice, not a forced one; a tabular method (page 3) would be just as happy with the Discrete version, but a Box generalizes better to a neural network and mirrors how the real project encodes its own state as a vector of features rather than one big enumerated index.

Next, reset(). It has exactly one job: put the agent back at the start and hand back the first observation.

    def reset(self, seed=None, options=None):
        super().reset(seed=seed)
        self._row, self._col = 0, 0
        self._steps = 0
        return self._get_obs(), {}

    def _get_obs(self):
        return np.array([self._row / (GRID_SIZE - 1),
                          self._col / (GRID_SIZE - 1)], dtype=np.float32)

Pulling the observation-building into its own _get_obs() helper rather than inlining it in both reset() and step() is a small habit worth adopting early — the real F1StrategyEnv._get_obs() (page 7) exists for exactly this reason: one place that builds the vector, called from everywhere that needs one.

Now step(), movement first. Apply the action, then clamp the result to the grid so the agent can't walk off the edge:

    def step(self, action):
        assert self.action_space.contains(action)

        if action == UP:
            self._row = max(0, self._row - 1)
        elif action == DOWN:
            self._row = min(GRID_SIZE - 1, self._row + 1)
        elif action == LEFT:
            self._col = max(0, self._col - 1)
        elif action == RIGHT:
            self._col = min(GRID_SIZE - 1, self._col + 1)

Then the reward and the two ways an episode can end. Every step costs -1 — the standard way to encourage a shortest-path solution, since the return is maximized by reaching the goal in as few steps as possible. Reaching the goal terminates the episode (the task genuinely finished). Running out of steps without reaching it truncates instead — the distinction page 4's opening section named but didn't yet have a live example for:

        self._steps += 1
        at_goal = (self._row == GRID_SIZE - 1) and (self._col == GRID_SIZE - 1)

        reward = -1.0
        terminated = at_goal
        truncated = (self._steps >= MAX_STEPS) and not at_goal

        return self._get_obs(), reward, terminated, truncated, {}

That's the whole class: __init__, reset(), _get_obs(), and step(), assembled in that order under class GridWorldEnv(gym.Env):. Now run it:

if __name__ == "__main__":
    from stable_baselines3.common.env_checker import check_env
    env = GridWorldEnv()
    check_env(env)   # raises if the Gymnasium contract is violated

    obs, info = env.reset(seed=0)
    total_reward = 0.0
    print(f"start  obs={obs}")
    for t in range(MAX_STEPS):
        action = RIGHT if t % 2 == 0 else DOWN   # zig-zag toward the goal
        obs, reward, terminated, truncated, info = env.step(action)
        total_reward += reward
        print(f"step {t+1:2d}  action={action}  obs={obs}  reward={reward:.1f}")
        if terminated or truncated:
            print("terminated" if terminated else "truncated")
            break
    print(f"episode return: {total_reward:.1f}")

Running it prints one line per step, the agent's position visibly approaching [1.0, 1.0] (the bottom-right corner in normalized coordinates), and a final terminated once it arrives. Change the zig-zag policy to something that never reaches the corner — say, always UP — and watch truncated fire instead once MAX_STEPS runs out, with a worse (more negative) total return, since the episode ran the full length without ever reaching the goal. That contrast is the cheapest way to actually feel why Gymnasium keeps terminated and truncated as two separate booleans rather than collapsing them into one "episode over" flag.

check_env: validating the contract

Stable-Baselines3 ships a utility, check_env (used in the script above), that runs an environment through a battery of sanity checks — do reset() and step() return the right types and shapes, do observations stay within the declared bounds, does the reward come back as a plain number. Passing check_env is a necessary, not sufficient check: it verifies your environment obeys the interface, not that your physics (grid movement, or in the real project, lap times and tyre degradation) is correct.

This project

check_env is a Definition-of-Done item precisely because interface bugs (returning a float64 where float32 was declared, an observation that briefly exceeds 1.0 from a rounding edge case) are easy to introduce silently and hard to spot by eye, but check_env catches them immediately.

Action masking in Gymnasium

Gymnasium's core spec doesn't have a first-class notion of "some actions are invalid right now" — the convention used by sb3-contrib's MaskablePPO is a separate method, action_masks(), exposed alongside step() and reset(), returning a boolean array the same length as the action space. Algorithms that support masking call this every step and exclude False actions. Algorithms that don't will happily attempt invalid actions.

GridWorld above didn't need this — walking into a wall was handled by clamping the position rather than by forbidding the action, which is a perfectly valid design choice for a grid but a poor fit once "invalid" has real consequences (page 6: pitting for the compound you're already on, running an intermediate tyre in the dry). Where clamping silently absorbs a bad action into a no-op, masking prevents the agent from taking it at all — the right choice whenever an action is invalid for a reason the agent should learn to recognize, not just a boundary to bounce off of.

This project

This is exactly why Phase 1 keeps the −500 terminal penalty in step() as a defence-in-depth backstop, in case an agent or a bug bypasses action_masks() entirely.

render_mode and rendering

Environments can optionally implement a render() method (declared via metadata = {"render_modes": [...]}) to produce a visualization — useful for debugging, not required for training. Phase 1 declares render_modes = ["human"] but the actual dashboard work is deferred to a later phase; Phase 1 only needs the declaration to exist so the class is well-formed.

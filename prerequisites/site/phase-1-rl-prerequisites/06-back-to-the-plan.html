F1StrategyEnv.step() does the bookkeeping, with page 05's ordering rule: the stop is charged to the lap being finished, on the tyre it started on, and the new tyre and its warm-up start next lap. Two parts of P are drawn at every reset(): weather from real race traces (ScenarioLoader) and safety cars fresh from a hazard rate (SafetyCarSampler), never replayed, for page 01's reason.

R is -lap_time on every lap, safety cars included, plus the −500 backstop. γ is 1.0, for pages 02 and 03's reasons.

Five rules, one mask

compute_action_mask returns one true/false value per action, and the environment and the Phase 3.5 oracle call the same function:

  1. Slicks (SOFT, MEDIUM, HARD) only in DRY or DAMP.
  2. INTERMEDIATE only in DAMP or WET.
  3. WET only in WET.
  4. No pitting for the compound you are on.
  5. STAY_OUT is switched off when the two-compound rule is not yet met and two laps remain, unless the race is declared wet, which voids the rule (the real regulation).

Where the code will go

Everything in dynamics.py is a pure function: inputs passed in, a value returned, no class state, no side effects. Three callers need the same physics: the live environment, the hand-written baselines, and the Phase 3.5 oracle, which asks for lap times in states no live race has been in. A pure function can be called from anywhere with the same answer and nothing to keep in sync. A method on the environment would tie the physics to one race.

The Definition of Done says it outright: no lap-time or masking logic is duplicated anywhere outside dynamics.py. An oracle that solves a slightly different race from the one agents train in gives numbers that look authoritative and are wrong, while both versions look right on their own.

Deep divef1_strategy_env.py, method by method180 words

The class holds the state a race has (lap, compound, tyre age, compounds used, this episode's weather and safety-car trace), and each method reads it, calls dynamics.py for any physics, and writes back.

  • __init__ loads calibration.json and builds Box(16,) and Discrete(6). No episode state: that is reset()'s job.
  • reset() samples weather and safety car independently, sets tyre_age = 1 (lap 1 is an out-lap: cars start on tyres fitted on the grid), and honours options={"starting_compound": ...} and the curriculum hook.
  • step() holds the ordering rule: time the lap on the old tyre, add the pit loss, then switch compound and reset the age.
  • _get_obs() builds the 16 numbers and asserts their shape and [0, 1] bounds on every call, not only in tests, which catches a scaling bug the moment it appears.
  • action_masks() calls dynamics.compute_action_mask and reimplements nothing.
  • _get_info() returns the public contract. info.get(...) returns None on a missing key instead of raising, so renaming a key breaks every later phase without an error. Adding keys is safe; renaming or removing one is a breaking change.

What the tests catch

The plan's test list is not a coverage quota. Each test guards one way an earlier draft went wrong:

  • test_return_equals_negative_race_time: page 03's identity, return = −race time, holds in code.
  • test_pit_lap_runs_on_old_tyre: the ordering rule was not inverted.
  • test_sc_timing_is_not_memorizable: safety cars are drawn fresh each episode (page 01).
  • test_cliff_is_capped: the cap caps, on every path.
  • test_action_mask_forces_pit_near_end and test_two_compound_rule_violation_penalty: the mask and the backstop each do their half of the two-compound rule.

Case 1 · the verdict

The head start is real, the plan removes it, and one test is caught in the crossfire

Is it a problem? Yes. The plan's own Step 3g says so: with γ = 1 and about −95 a lap over 52 laps, the true Q-values are about −5,000. A table that starts at 0 needs dozens of visits per state to travel that far, and it is "the most likely cause of 'training runs but nothing is learned' in Phases 4 and 5".

Is it a bug in the plan? No. Step 3g fixes it, by default: reward_offset: str = "base_pace" makes the reward -(lap_time - base_pace), so rewards sit near −5 a lap and Q-values near −250. On the Pit Wall the same move takes the start from −231.92 to −31.92.

Does the fix change a single pit stop? No. It shifts every policy's return by base_pace × total_laps, the same for all of them (page 03), and info["lap_time"] stays in real seconds for everything that reports.

The loose end. The plan's test fixture builds F1StrategyEnv(...) without a reward_offset, so every test gets the centred default. test_return_equals_negative_race_time adds the rewards to the true lap times and expects zero. Under the default it gets total_laps × base_pace instead (52 × 92 = 4,784 with this course's constants) and fails. The Definition of Done already says this test "runs with reward_offset="none""; the test as written does not. The fix is one line: build that test's environment with reward_offset="none". The prerequisites do not edit the plan; this goes to whoever implements Phase 1.

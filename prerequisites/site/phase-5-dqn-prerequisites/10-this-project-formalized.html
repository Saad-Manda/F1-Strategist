Two things this table turns up

β never gets near 1. The buffer raises β by one tick each time sample() is called, and the schedule is 500,000 ticks long. The run calls sample() about 64,750 times. So β ends at 0.4 + 0.6 × 64,750 / 500,000 ≈ 0.48. The "full correction late in training" that page 07 described does not happen with these numbers. beta_steps should be about the number of updates in the run.

The PER settings are not in the config. alpha and the three beta values are absent from configs/dqn.yaml, and the agent builds its buffer with only a capacity, so the buffer's own defaults apply. The Definition of Done asks for every hyperparameter to be in the config. The trunk-to-head width of 64 and max_norm are hardcoded in the same way.

Neither of these is in the plan's Risks table or the audit. They came out of doing this page's arithmetic, and are worth raising when the phase is built.

The reward the network trains on

The plan's first and most emphatic risk is page 08's trap, and its mitigation is the same switch Phase 4 used: build the environment with reward_offset="base_pace", so targets sit near −250 and not near −5,000. Race times in every table and chart are read from info["lap_time"] and are never centred.

Issues recorded against the real plan

All four are in the plan's Risks table or the audit. Each is a design lesson with a recognisable shape.

Evaluated agent still exploring

select_action branches on self.epsilon, and nothing in evaluate.py turns exploration off. At the floor of ε = 0.05 over 52 laps, an "evaluated" agent takes 0.05 × 52 ≈ 2.6 random actions per race, and some of those are 18-second pit stops its policy would never choose. This is the same class of mistake as the leak on Phase 4 page 08: a training-time mechanism left on during evaluation, quietly worsening every reported number. The fix is an explicit eval_mode flag that forces greedy selection, set by the evaluation code, with a test that two evaluation runs on one seed give identical races.

New transitions: the exponent applied twice

The bug from page 07, reproduced on page 09 stage 5. add() reads the largest leaf, which already holds p^α, and stores that value raised to α again. The fix is to store the largest leaf as it is. Page 09 showed why no reward curve will reveal it.

One counter, two owners

self._step is increased only inside decay_epsilon(). update() reads the same counter to decide whether this is a fourth step. The two methods are joined by nothing except the order the training loop happens to call them in. If a caller ever skips decay_epsilon(), as an evaluation loop reasonably would, update() either fires on every call or never fires. Nothing is wrong today. It is a coupling that nothing enforces, and the fix is to count steps in one place that both methods are documented to depend on.

Unseeded randomness

select_action and the buffer's sample() draw from NumPy's global random state. The project's rule is that every source of randomness takes a seed, because paired-seed comparison depends on it. Both should draw from a seeded generator the agent owns, the way page 09's toy passes one rng to its learner and its memory.

The plan is explicit about one outcome that would otherwise look like failure. This state space is small. A table with fine enough bins can represent the answer, and page 01's argument for a network is about what happens when dimensions are added.

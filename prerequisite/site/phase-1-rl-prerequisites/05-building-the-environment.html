Page 05 / 08 — Building it yourself

Building the Environment, Step by Step

The same piece-by-piece method page 4 used on GridWorld, applied to a new, race-flavoured toy — one complication added at a time, never a whole class dumped at once.

Page 4 built GridWorldEnv — a standard, domain-agnostic environment — piece by piece: constants and spaces first, then reset(), then step() split into its movement half and its reward/termination half. This page uses the same piece-by-piece method on a new, race-flavoured toy, adding one real-world complication at a time: multiple tyre compounds trading pace for life, a wear cliff, fuel burning off, weather punishing the wrong tyre, a pit stop charged to the old tyre rather than the new one, a safety car that arrives at random, and rules about which actions are even legal.

Every function and class name below is invented for this page (toy_pace, toy_wear, ToyRaceEnv, and so on) and deliberately does not match any name in dynamics.py or f1_strategy_env.py. The goal is to arrive at the same shape of solution independently, so that when you later open the real files (page 6 grounds them, page 7 reads them) you recognise the structure because you built something like it yourself.

At every stage, only the new or changed piece is shown — never the whole class again. Assemble each piece into the running script yourself as you go; typing it in rather than copy-pasting a finished block is a large part of where the understanding comes from.

Stage 1 — one compound, the GridWorld way

Start from exactly the shape page 4 used: constants and spaces, then reset() with a _get_obs() helper, then step() split into two halves.

Constants and the class shell:

import numpy as np
import gymnasium as gym
from gymnasium import spaces

STAY_OUT, PIT = 0, 1
HORIZON = 10
PIT_LOSS = 2.0

class ToyRaceEnv(gym.Env):
    metadata = {"render_modes": []}

    def __init__(self):
        super().__init__()
        # obs = [tyre_age_normalized] -- one feature, in [0, 1]
        self.observation_space = spaces.Box(low=0.0, high=1.0, shape=(1,), dtype=np.float32)
        self.action_space = spaces.Discrete(2)   # STAY_OUT | PIT

reset() and its _get_obs() helper — the same pattern as GridWorld, for the same reason: one place builds the observation vector, called from everywhere that needs one.

    def reset(self, seed=None, options=None):
        super().reset(seed=seed)
        self._lap = 1
        self._age = 1
        return self._get_obs(), {}

    def _get_obs(self):
        return np.array([min(self._age / HORIZON, 1.0)], dtype=np.float32)

step(), the timing half first — compute this lap's time from the current tyre age, before anything about the action changes state:

    def step(self, action):
        assert self.action_space.contains(action)
        lap_time = 1.0 + 0.05 * (self._age ** 2)   # quadratic wear
        if action == PIT:
            lap_time += PIT_LOSS

Then the bookkeeping half — apply the action, advance the lap, and return:

        if action == PIT:
            self._age = 0
        self._age += 1
        self._lap += 1

        reward = -lap_time
        terminated = self._lap > HORIZON
        info = {"lap_time": lap_time, "age": self._age}
        return self._get_obs(), reward, terminated, False, info

Assemble those four pieces under class ToyRaceEnv(gym.Env): in order, add a small if __name__ == "__main__": driver like page 4's (reset, loop step() for HORIZON laps, print each lap's reward), and run it. Everything from here modifies this skeleton.

Stage 2 — more than one tyre: pace vs. life

Real tyres aren't interchangeable — a grippier compound is faster when fresh and wears out sooner; a harder compound is slower but lasts. Without that trade-off, "which tyre" isn't a real decision.

First, just the data and the two pure functions — no class changes yet:

# Each compound: (pace_penalty, wear_rate). A is faster but wears quicker than B.
COMPOUNDS = {
    "A": {"pace": 0.0, "wear_rate": 0.09},
    "B": {"pace": 0.6, "wear_rate": 0.03},
}

def toy_pace(compound: str) -> float:
    """Fixed pace penalty of a compound relative to the fastest one."""
    return COMPOUNDS[compound]["pace"]

def toy_wear(compound: str, age: int) -> float:
    """Quadratic wear, rate depends on which compound is fitted."""
    return COMPOUNDS[compound]["wear_rate"] * (age ** 2)

Now the three places ToyRaceEnv has to change to use them. The spaces grow by two (one-hot for which compound is fitted), and the action space grows by one (PIT_A/PIT_B instead of a single undifferentiated PIT):

STAY_OUT, PIT_A, PIT_B = 0, 1, 2

    def __init__(self):
        super().__init__()
        # obs = [tyre_age_norm, compound_is_A, compound_is_B]
        self.observation_space = spaces.Box(low=0.0, high=1.0, shape=(3,), dtype=np.float32)
        self.action_space = spaces.Discrete(3)

_get_obs() needs to report which compound is fitted, alongside the age it already tracked:

    def _get_obs(self):
        onehot = [1.0, 0.0] if self._compound == "A" else [0.0, 1.0]
        return np.array([min(self._age / HORIZON, 1.0), *onehot], dtype=np.float32)

And step()'s timing half now calls the two new functions instead of a single hardcoded formula, while reset() picks a starting compound and the bookkeeping half switches on whichever PIT_* action was taken:

        lap_time = 1.0 + toy_pace(self._compound) + toy_wear(self._compound, self._age)
        ...
        if action == PIT_A:
            self._compound, self._age = "A", 0
        elif action == PIT_B:
            self._compound, self._age = "B", 0

(reset() additionally sets self._compound = "A" alongside self._age = 1.) Run it with a policy that switches to B partway through and watch the total return change — that's the same compound-choice trade-off page 2's worked example computed by hand.

Stage 3 — a wear cliff, capped

Real degradation isn't smoothly quadratic forever — tyres are fine for a while, then fall off a cliff, then the damage plateaus. Model that as two pieces: gentle linear wear below an age threshold, a steep — but capped — penalty above it. Only toy_wear and the COMPOUNDS data change; nothing else in the class does:

COMPOUNDS = {
    "A": {"pace": 0.0, "wear_rate": 0.05, "cliff_age": 4, "cliff_severity": 0.15, "cliff_cap": 4.0},
    "B": {"pace": 0.6, "wear_rate": 0.02, "cliff_age": 7, "cliff_severity": 0.08, "cliff_cap": 4.0},
}

def toy_wear(compound: str, age: int) -> float:
    """
    Piecewise wear: linear below the cliff age, a squared-and-capped
    penalty above it. The cap matters: without one, a single very old
    tyre can produce a wear number so large it swamps every other
    signal in the reward, and every other decision stops mattering.
    """
    c = COMPOUNDS[compound]
    linear = c["wear_rate"] * age
    over = max(0, age - c["cliff_age"])
    cliff = min(c["cliff_severity"] * (over ** 2), c["cliff_cap"])
    return linear + cliff

Before wiring it back in, print toy_wear("A", age) on its own for age = 1..16 and look at the numbers: flat-ish, then a knee around the cliff age, then flattening out again as the cap takes over — never blowing up further no matter how old the tyre gets. Only once that shape looks right does it make sense to rerun the full environment (with a longer HORIZON, say 16, so the cliff has room to show up in an episode).

Stage 4 — fuel burning off

A car gets faster as it burns fuel over the race — a real, separate effect from tyre wear, and one that doesn't depend on which tyre is fitted at all. One new function:

def toy_fuel_penalty(laps_left: int) -> float:
    """Heavier car = slower lap. Burns off linearly as the race goes on."""
    FUEL_PER_LAP = 0.08     # kg-equivalent burned per lap, in toy units
    SENSITIVITY = 0.02      # seconds of penalty per unit of fuel remaining
    return (laps_left * FUEL_PER_LAP) * SENSITIVITY

And one line added to step()'s timing half:

        lap_time += toy_fuel_penalty(HORIZON - self._lap)

Print toy_fuel_penalty(laps_left) for laps_left = HORIZON down to 0 before wiring it in — it should shrink smoothly to exactly zero at the finish, which is the toy equivalent of the real project's fuel effect vanishing on the last lap.

Stage 5 — weather, and the wrong tyre for it

Introduce a second axis entirely separate from tyre choice: track conditions. First, just the penalty table and its lookup function:

DRY, WET = 0, 1

# Penalty for running each compound in each condition. Large off-diagonal
# terms are the point: the wrong tyre for the weather should be costly
# enough that the agent has to actually track the weather, not ignore it.
WEATHER_PENALTY = {
    DRY: {"A": 0.0, "B": 0.0},
    WET: {"A": 6.0, "B": 5.5},   # both toy dry compounds are bad in the wet
}

def toy_weather_penalty(weather: int, compound: str) -> float:
    return WEATHER_PENALTY[weather][compound]

Then the observation grows by two more (a weather one-hot), reset() samples a weather value for the episode (held fixed for the whole toy episode to keep this stage simple — the real plan varies it lap-by-lap from a historical trace, which you don't need to reproduce to get the idea: self._weather = self.np_random.integers(0, 2)), and step()'s timing half gets one more added term:

        lap_time += toy_weather_penalty(self._weather, self._compound)

Run one episode with self._weather forced to WET and watch every lap get visibly slower regardless of which compound is fitted — that's the mismatch penalty doing its job.

Stage 6 — the pit-lap ordering rule

This is the subtlest stage, and the easiest one to get backward by accident. A pit stop happens at the end of a lap: the driver completes the whole lap on the old tyre, then peels into the pits. So the lap just driven should be timed on the old compound at its old age, and only the next lap should reflect the new tyre — including a fresh out-lap warmup penalty for being cold.

First, the warmup function on its own:

def toy_warmup(age: int) -> float:
    """Cold-tyre penalty: full on the out-lap, half the next lap, gone after."""
    if age <= 1:
        return 1.2
    if age == 2:
        return 0.5
    return 0.0

Then the timing half of step(), now complete — every term so far, all evaluated against the state before any pit stop is applied:

        lap_time = (1.0
                    + toy_pace(self._compound)
                    + toy_wear(self._compound, self._age)
                    + toy_fuel_penalty(HORIZON - self._lap)
                    + toy_weather_penalty(self._weather, self._compound)
                    + toy_warmup(self._age))
        if action != STAY_OUT:
            lap_time += PIT_LOSS

And only now, the bookkeeping half — the pit stop takes effect strictly after lap_time above has already been computed:

        if action == PIT_A:
            self._compound, self._age = "A", 0
        elif action == PIT_B:
            self._compound, self._age = "B", 0
        self._age += 1
        self._lap += 1

Try writing it the wrong way round — switch the compound before computing lap_time — and watch what happens to a pit lap's cost: it drops, because the pit lap would then get the new tyre's fresh pace and dodge the old tyre's wear and dodge the out-lap warmup, all at once, while also paying pit loss. Comparing the two versions side by side is the fastest way to feel why this ordering is a real bug class, not a stylistic preference.

Stage 7 — a safety car that isn't scripted

So far every episode with the same starting conditions plays out identically except for the agent's own choices. Add something genuinely random. First, the sampler on its own, completely separate from the environment class:

HAZARD_PER_LAP = 0.06     # chance any given green lap starts a safety car
SC_DURATION_MEAN = 3
SC_PIT_DISCOUNT = 0.4     # pitting under SC costs this fraction of the normal loss

def sample_sc_trace(horizon: int, rng: np.random.Generator) -> np.ndarray:
    """
    Independently, each green lap has a HAZARD_PER_LAP chance of starting
    a safety car that then runs for a random duration. Sampled fresh every
    call -- two episodes should very rarely have the SC on the same laps.
    """
    trace = np.zeros(horizon, dtype=bool)
    lap = 0
    while lap < horizon:
        if not trace[lap] and rng.random() < HAZARD_PER_LAP:
            duration = max(1, int(rng.normal(SC_DURATION_MEAN, 1)))
            trace[lap:lap + duration] = True
            lap += duration
        else:
            lap += 1
    return trace

Before touching the environment, call this on its own five times with different seeds and print the resulting trace each time — confirm the safety car really does land on different laps almost every call. Only once that's visibly true does it earn a place in reset():

        self._sc_trace = sample_sc_trace(HORIZON, self.np_random)

Then step() gets one new branch at the very top, before any of Stage 6's terms:

        if self._sc_trace[self._lap - 1]:
            lap_time = 8.0   # fixed, slow flag-lap time -- no term above applies
            if action != STAY_OUT:
                lap_time += PIT_LOSS * SC_PIT_DISCOUNT
        else:
            lap_time = (1.0 + toy_pace(...) + ...)   # Stage 6's full formula
            if action != STAY_OUT:
                lap_time += PIT_LOSS

The point of sampling fresh every episode rather than reusing one fixed trace: an agent that could memorise "the SC always comes on lap 6" would learn a lookup table, not a strategy.

Stage 8 — action masking

Not every action is legal in every situation. Build the mask function up rule by rule rather than all at once. First, just the "can't repeat the current compound" rule:

def toy_action_mask(compound, weather, laps_left, compounds_used) -> np.ndarray:
    mask = np.array([True, True, True])   # STAY_OUT, PIT_A, PIT_B
    if compound == "A":
        mask[PIT_A] = False
    else:
        mask[PIT_B] = False
    return mask

Then add the weather rule — suppose B is unsafe in the wet in this toy world:

    if weather == WET:
        mask[PIT_B] = False

Then the "must use both compounds eventually" rule:

    if len(compounds_used) < 2 and laps_left <= 1:
        mask[STAY_OUT] = False

And finally a safety net, so the function never returns "nothing is legal":

    if not mask.any():
        mask[STAY_OUT] = True
    return mask

Wire this up as an action_masks() method exactly like page 4's toy did, but this time it actually forbids things. Try running a random policy (env.action_space.sample()) with and without respecting the mask, and compare how often each version ends the toy race having never used compound B — that's the concrete difference masking makes.

Stage 9 — centring the reward

With enough laps and consistently negative per-lap rewards, the total return can get large in magnitude (page 3 covers why that's a learning-speed problem). The fix doesn't need to live inside the environment's core logic — wrap it:

class RewardCentringWrapper(gym.Wrapper):
    """Subtracts a fixed constant from every step's reward. Does not change
    which policy is optimal (page 3's proof) -- only the scale of the numbers."""
    def __init__(self, env, offset: float):
        super().__init__(env)
        self.offset = offset

    def step(self, action):
        obs, reward, terminated, truncated, info = self.env.step(action)
        info["true_reward"] = reward          # keep the real number available
        return obs, reward + self.offset, terminated, truncated, info

env = RewardCentringWrapper(ToyRaceEnv(), offset=1.5) shifts every episode's return by the same fixed amount without touching the environment's own code at all — a clean illustration of an important general pattern: a transformation that changes training signal without changing the environment's actual physics belongs in a wrapper, not baked into step().

Stage 10 — what you've built

Stages 1 through 9, assembled, form a small but complete environment with the same shape as a real pit-strategy MDP: multiple compounds trading pace for life, a capped wear cliff, fuel burn-off, weather mismatch, correctly-ordered pit stops with warmup, a freshly-sampled safety car with a discounted pit, action masking, and an optional reward-centring wrapper. Nothing about the numbers, the exact function names, or the file organisation matches the real project — and it shouldn't. The value of this stage isn't a finished script sitting in front of you; it's that every piece of it passed through your own hands, in an order where each new complication made sense on its own before the next one was added.

That's the preparation page 6 assumes. It won't repeat any of the code above — instead it names which piece of the real dynamics.py and f1_strategy_env.py corresponds to which stage here, so you can go read the real files already knowing what each part is for.

Lambdas, Multiprocessing, and a Windows-Fatal Pickling Bug

A general lesson about closures and process boundaries first, then the specific line in the real plan that will not run on this machine.

The general lesson

SubprocVecEnv (page 06) has to get "how to build this environment" into each of its worker processes. Unlike threads, separate processes do not share memory — the only way to hand a process a function or an object is to pickle it: serialize it to bytes, ship those bytes across, and reconstruct the object on the other side. Python's pickle can serialize a plain function defined at module level, because all it actually stores is "import this module, look up this name" — reconstructing it on the other end is just repeating that lookup. A lambda, or any closure, has no such name to look up. There is nothing for pickle to store except a description that cannot survive the process boundary, so pickling one fails.

The specific bug

Quoted directly from the real plan's make_vec_masked_envs:

masked_env = ActionMasker(env, lambda e: e.action_masks())

This lambda has to cross into each SubprocVecEnv worker process as part of the environment-construction closure, and — per the general lesson above — it cannot.

Why this is easy to miss in testing

The sharpest part of the lesson

Linux's default process-start method, fork, copies the entire parent process's memory into the child — lambda and all — so this exact bug can silently pass on a Linux machine, or in many Linux-based CI containers, without ever being noticed. This project runs on Windows, whose only available start method is spawn: a genuinely fresh Python interpreter that re-imports the target module from scratch and must actually pickle everything handed to it. The same code that appears to work fine on a colleague's Linux laptop raises PicklingError reliably here.

Generalized beyond this one bug: any failure whose reproduction depends on the operating system's process-start method is invisible until someone happens to run the code on the other kind of OS. That's worth checking for proactively — searching for lambdas or closures passed into anything that will cross a process boundary — rather than discovering it only when a training run crashes on the machine the project actually deploys to.

The fix

Replace the lambda with a named function defined at module level:

def _mask_fn(env) -> np.ndarray:
    return env.action_masks()

masked_env = ActionMasker(env, _mask_fn)

This pickles as "import this module, get the name _mask_fn" — trivially reconstructable in a fresh spawned process, because the name and the module both genuinely exist independently of any particular closure.

A second option, tied back to page 06's tradeoff

The real plan's own Risks table names a fallback worth taking seriously rather than treating as a mere workaround: given how cheap one F1StrategyEnv.step() call actually is (a handful of arithmetic operations, no heavy simulation), the inter-process-communication overhead SubprocVecEnv introduces may well cost more than the parallelism saves. DummyVecEnv sidesteps the pickling problem entirely (everything stays in one process, so nothing needs to cross a process boundary) and is plausibly the faster choice here once IPC overhead is actually measured rather than assumed away — page 06's generic tradeoff, resolved concretely for this specific environment.

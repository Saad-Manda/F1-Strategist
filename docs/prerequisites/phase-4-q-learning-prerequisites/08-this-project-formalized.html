The reward-scale problem, argued numerically

The same style of argument Phase 1 page 3 used to prove reward centring doesn't change the optimal policy applies here, with a training-speed consequence layered on top. With γ = 1 and a per-lap reward of roughly −95 seconds over a ≈52-lap race, the true Q-values the table needs to learn are around −95 × 52 ≈ −5,000. The table initializes every cell at 0.

distance a cell must travel: 0 → ≈ −5,000 per-update step size at α = 0.1: roughly 10% of the remaining gap, each visit a cell needs dozens of visits just to get within a small fraction of −5,000, and the value has to propagate backward, lap by lap, before early-race cells see any signal at all — exactly the mechanism page 2's hand-run showed for a table this size, stretched out over a race-length horizon

This is the single most likely cause of "the agent trains without error but the learning curve never moves" — not a bug in the update rule, but a scale mismatch between how far a cell needs to travel and how far a realistic number of visits at α = 0.1 can move it in the time available. The fix is Phase 1's own reward_offset="base_pace" wrapper, which learns on −(lap_time − base_pace) instead of raw lap time — a per-step reward around −5 rather than −95, and Q-values around −250 rather than −5,000. This is safe for exactly the reason Phase 1 page 3 proved: subtracting a constant from every step's reward over a fixed horizon shifts every policy's total return by the same fixed amount, and shifting every option's value equally can never change which one is the argmax.

Why "+10 optimistic init" isn't the fix

The real plan's Risks table suggests an optimistic +10 initialization bonus for pit actions to encourage early exploration of pitting. Against a −5,000-scale problem, +10 is a rounding error — it nudges the very first visit to a pit-action cell by an amount roughly 0.2% the size of the gap that cell needs to close. It is not a substitute for fixing the reward scale; it's a reasonable secondary nudge to apply after reward_offset="base_pace" has already brought the true values down to a range where a small initialization bonus can plausibly matter.

Curriculum learning, concretely

docs/idea.md's sequencing tip — train on the easy case before the full scenario library — becomes a two-switch options flag passed to env.reset() for the first curriculum_episodes episodes of training: filter scenario sampling to DRY weather traces only, and force an all-green safety-car trace (both switches are needed because, under the revised environment design, safety cars are sampled stochastically rather than replayed from a fixed trace — filtering weather alone wouldn't also suppress SC events). In terms specific to this state space: restricting to dry, no-SC episodes early in training holds weather_regime and safety_car_active effectively constant, so early training concentrates its limited number of episodes on fewer distinct table cells — more visits per cell, faster movement away from the all-zero start discussed above — before the full scenario library reintroduces the dimensions that were held fixed.

Two bugs recorded against the real plan

Both are design lessons a reader who did page 7's exercises will already recognize the shape of, not just warnings to memorize:

Evaluated agent still exploring

select_action branches on self.epsilon at every call, and nothing in evaluate.py ever turns exploration off before running a trained agent's evaluation races. At the trained floor ε = 0.05 and a ≈52-step race, the expected number of random actions per evaluated race is 0.05 × 52 ≈ 2.6 — not a rare edge case but a near-certainty on every reported race, some of those random draws landing on a full 18-second pit stop the agent's actual policy would never have chosen. The fix is an explicit eval_mode / deterministic flag that forces pure-greedy action selection, set by evaluate_agent before any comparison run, with a test asserting two evaluation runs on the same seed produce byte-identical trajectories.

The SARSA pre-commit leak, for real

The exact bug reproduced on page 7 stage 6: SARSAAgent._next_action has no reset() and nothing in the training or evaluation loop clears it between episodes, so a pre-committed action chosen for the previous episode's final state can be returned as the very first action of a completely different race — a stale decision applied to an observation it was never chosen for. The fix mirrors what page 7 stage 6 demonstrates is missing: add reset() to SARSAAgent and call it at the start of every episode, both during training and evaluation.

The optimality-gap metric, with real numbers to reference

Carried over unchanged from Phase 3.5: optimality_gap = mean_race_time(agent) − mean_race_time(Oracle B), in seconds, with a paired bootstrap confidence interval. The real Definition of Done's "≥60/100 seeds beating the threshold baseline" is the necessary-but-not-sufficient bar — a trained agent that clears it has shown it learned something better than a fixed heuristic, but the actual headline result this phase reports is how much of the gap between that baseline and the Phase 3.5 DP oracle's exact optimum the agent closed. A Q-learning agent that beats the baseline on 61/100 seeds while leaving most of the baseline-to-oracle gap unclosed has technically passed the DoD bullet and still failed the phase's real pedagogical point.

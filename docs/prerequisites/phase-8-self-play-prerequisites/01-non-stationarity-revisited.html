When the Opponent Learns Too: Non-Stationarity, Revisited

Phase 6 page 07 explained why scripted rivals sidestep this problem. Phase 8 removes that shield on purpose.

A quick recap of the shield

Standard RL theory — everything Phase 4 and 5 rely on — assumes the environment is stationary: the same state, visited at two different times, produces the same distribution over next states and rewards. Phase 6's rivals follow a predetermined pit_laps plan with no learning update of their own, so from the agent's point of view they're part of a fixed environment, exactly like the weather trace or the safety-car process. All of Q-learning and DQN's convergence arguments keep applying unmodified — only the state and reward got bigger.

What breaks once the opponent is also learning

Phase 8 lets two (or more) copies of the same kind of learner train against each other. Now the "environment," from any one agent's point of view, includes the other agent's policy — and if that policy is changing over time, so is everything the first agent is trying to learn. A pit-under-safety-car move that worked well against last week's opponent policy might not work at all against this week's, purely because the opponent adapted, not because anything about the track, tyres, or weather changed. The transition dynamics the agent's Q-learning update is trying to converge on are themselves moving under it.

A second, sharper reason experience replay needs care here

Phase 5 justified experience replay by breaking the temporal correlation between consecutive transitions. Self-play adds a second reason to be careful with it: a transition collected against an old opponent checkpoint describes a game that, strictly, no longer exists once that opponent has been replaced by a newer one in the pool. Replaying it later trains the learner against a summary of a game state that isn't the one it will actually face next. This doesn't mean replay has to be abandoned — page 03's checkpoint pool is part of how the real plan manages this — but it's worth naming as a second source of staleness beyond Phase 5's original one.

Three ways to structure multi-agent training

Given that more than one agent is learning at once, there's a genuine design choice in how their learning is organized. Three points on that spectrum, briefly:

  • Independent learners. Each agent has its own separate value function (its own DQN, its own replay buffer, its own weights) and learns purely from its own experience, with no communication between agents and no shared network. From any one agent's perspective, every other agent is just part of a — now nonstationary — environment. This is the simplest setup and the one the real plan uses.
  • Parameter sharing. All agents use one shared network, trained on the combined experience of everyone. This tends to learn faster, because experience is pooled, but it implicitly assumes the agents are meaningfully symmetric (interchangeable roles) — true here, since every car runs the same strategy problem, but the real plan doesn't exploit this.
  • Centralized-training, decentralized-execution (CTDE). A shared value function (often a "centralized critic") sees the full joint state of every agent during training, while each agent still acts on its own local observation at execution time. This is more powerful — it can directly represent how one agent's action affects another's return — and more complex to implement (the more sophisticated MARL methods, such as MADDPG, are built this way).

Why independent learners is the deliberate choice here, not a corner cut: Phase 5's DuelingDoubleDQNAgent already exists as a complete, working single-agent learner. The real plan reuses it completely unmodified, one instance per car, and treats coordination-shaped behavior — the undercut, the overcut — as something that should emerge from the environment's own payoff structure (once page 06's blocking model exists) rather than something engineered into a shared critic. It's the simplest setup that can, in principle, still produce the interesting result.

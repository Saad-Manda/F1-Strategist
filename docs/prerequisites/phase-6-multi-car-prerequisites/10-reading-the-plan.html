Page 10 / 11 — Reading a plan critically

Reading the Implementation Plan's Code

Unlike every code-walkthrough page in the earlier prerequisite sets, this one points at a plan's pseudocode, not a file that has actually been built and run.

Why this page is different

Phase 6 hasn't been implemented — there is no src/env/f1_multi_env.py, rival.py, or overtaking.py in the repository yet. What follows reads the pseudocode inside .antigravity/plans/phase-6-multi-car-rivals.md itself. Part of the point of this page is that a plan's own code sample is not automatically correct just because it's written in a plan — pages 05 and 06 found a missing model and five bugs in it before a single line was ever run. Reading a plan this way, before implementation starts, is the whole reason those findings exist rather than being discovered three weeks into a confusing training run.

Reading order

rival.py's RivalState.advance_lap first — this is where E1's double-add lives (page 06), and where the plan's own cross-phase audit flags a second issue worth knowing before reading a line further: this file, as sketched in the Phase 6 plan, still calls compute_lap_time with Phase 1's original five-argument signature. Phase 1's revised contract dropped laps_since_pit and replaced safety_car_active: bool with track_status: int — rival.py needs updating for that before it will even run against the real dynamics module. Rivals also need to call compute_pit_loss(track_status, params) rather than reading params["pit_loss"] directly, or they pay full price for pit stops the agent gets at Phase 0.5's calibrated safety-car discount (this is E6d's flip side, from page 06 — rivals need the same discount mechanism, not just a reason to want to pit under SC).

Then overtaking.py, matched directly against page 04's two formulas — nothing new to look for here beyond confirming the constants (OVERTAKE_ATTEMPT_GAP = 1.0, DIRTY_AIR_MAX_GAP = 1.5, DIRTY_AIR_MAX_PENALTY = 0.5) match what page 04 worked through by hand.

Then f1_multi_env.py's step(), in the order page 06 introduced its findings: E2 (the overwritten overtake result), E3 (dirty air reaching the reward but not the lap time), E5 (the mislabeled potential_shaping branch), and E6a–d (the career-average pace_delta, the lap-index ordering, the leader gap sentinel, rivals ignoring safety cars).

A specific pointer: where page 05's fix belongs

f1_multi_env.py's multi-car lap-time computation, as sketched in the plan, has no blocking line at all — position is computed purely from cumulative time, with nothing in the dynamics that caps a trailing car's pace. Page 05's constraint (lap_time = max(own_lap_time, car_ahead_lap_time + dirty_air_penalty(gap))) needs to be added directly to the multi-car lap-time model, not left as a comment or a follow-up — every other piece of the file's overtaking and position logic depends on this constraint existing first, per page 05's argument that attempt_overtake has nothing to overcome without it.

What the plan's own listed tests would — and wouldn't — catch

Test (as listed in the plan)What it actually catchesWhat it misses
test_multi_env_positions_sum_correctlyEvery position from 1 to N is assigned exactly onceNeither E1 nor E2 — both bugs still leave some valid sorted ordering of positions, just the wrong one relative to what actually happened on track. A test that only checks the ordering is well-formed can pass while the ordering itself is meaningless.
test_dirty_air_penalty_at_zero_gap, test_dirty_air_penalty_zero_beyond_thresholdPage 04's formula, correct as written, at its two boundary valuesE3 entirely — these test the formula for dirty air, not whether its output ever reaches agent_lap_time. Both pass even with E3 present, because E3 is about a correctly-computed number never being applied, not about the number being wrong.
test_rival_uses_configured_pit_lapsA rival's tyre age resets to 1 on its scripted pit lapE1's accumulation bug — this test never inspects total_time, only tire_age.

The gap between "the plan's tests pass" and "the phase's goal is reachable"

None of the five tests already written into the plan would catch E4 — the missing blocking model, page 05's central finding — at all. Every one of them can pass in a world with no blocking constraint whatsoever, because none of them ever asks the question page 05's proposed new test asks: does being stuck behind a faster car actually cost anything? That's exactly why the real Definition of Done had to gain new, explicit entries for the blocking model and the overtake-changes-positions check (page 09), rather than trusting the original five tests to cover a finding that came from reading the pseudocode's design, not from running any of its code.

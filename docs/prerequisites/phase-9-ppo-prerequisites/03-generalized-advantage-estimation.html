Page 03 / 12 — A little math

Generalized Advantage Estimation (GAE-λ)

The advantage estimator Stable-Baselines3 actually uses — not in idea.md's own concept list, but silently load-bearing in the real config.

A gap this page exists to fill

Page 02 defined A(s,a) = Q(s,a) − V(s), but nothing in a single trajectory hands you Q(s,a) directly — it has to be estimated, and there is more than one way to do it, trading bias against variance exactly like Phase 4/5's n-step-vs-Monte-Carlo TD tradeoff (assumed background) generalizes.

Two extremes, already familiar

The 1-step TD residual, using the critic's own value estimates:

δ_t = r_t + γ·V(s_{t+1}) − V(s_t)

This is itself an advantage estimate — a low-variance one (it only depends on one sampled transition and the critic's current estimates), but biased whenever V is inaccurate, which it always is to some degree during training. At the other extreme sits the full Monte Carlo advantage from page 01/02, G_t − V(s_t) — unbiased (it uses the actual realized return, no bootstrapping at all) but high-variance, for the same reason page 01 originally motivated the critic in the first place.

GAE-λ: the interpolation

Generalized Advantage Estimation defines the advantage as an exponentially-weighted sum of every possible k-step advantage estimate at once:

A_t^GAE(λ) = Σ_{l=0}^∞ (γλ)^l · δ_{t+l}

λ is the dial. At λ = 0, every term beyond l=0 vanishes and the sum collapses to the pure 1-step estimate, δ_t. At λ = 1, the geometric weighting disappears ((γ·1)^l just tracks the usual discount) and the sum telescopes back into exactly the full Monte Carlo advantage, G_t − V(s_t). This is the same bias-variance dial as TD(λ) in Sutton & Barto — if that's already familiar from Phase 4's background, GAE is that same idea applied specifically to advantage estimation for a policy gradient rather than to value learning directly.

A hand-worked example

A 4-step episode, γ = 1.0 (this project's own convention for its fixed-length episodes). Rewards and the critic's value estimates at each visited state:

rewards: r0=−3 r1=−2 r2=−3 r3=−2 values: V(s0)=−10 V(s1)=−6 V(s2)=−5 V(s3)=−1 V(s4)=0 (terminal)

First, the TD residuals at every step:

δ0 = r0 + V(s1) − V(s0) = −3 + (−6) − (−10) = 1 δ1 = r1 + V(s2) − V(s1) = −2 + (−5) − (−6) = −1 δ2 = r2 + V(s3) − V(s2) = −3 + (−1) − (−5) = 1 δ3 = r3 + V(s4) − V(s3) = −2 + 0 − (−1) = −1

Now compute A_0^GAE(λ) at three values of λ, using (γλ)^l = λ^l since γ = 1:

λ = 0 (pure 1-step): A_0 = δ0 = 1.0 λ = 1 (pure Monte Carlo): A_0 = δ0 + δ1 + δ2 + δ3 = 1 − 1 + 1 − 1 = 0.0 Check against G_0 − V(s0): G_0 = −3−2−3−2 = −10, G_0 − V(s0) = −10 − (−10) = 0 ✓ matches λ = 0.95 (this project's SB3 default, see below): A_0 = δ0 + 0.95·δ1 + 0.95²·δ2 + 0.95³·δ3 = 1 + 0.95·(−1) + 0.9025·(1) + 0.857·(−1) = 1 − 0.95 + 0.9025 − 0.857 ≈ 0.095

The three answers genuinely differ: λ=0 reports an advantage of exactly the first residual, λ=1 reports the full-trajectory answer (which happens to be 0 here — this toy trajectory's rewards exactly matched the critic's own value estimates in total), and λ=0.95 lands close to, but not exactly at, the Monte Carlo end — consistent with putting most of its weight on the nearby residuals while still discounting the far ones.

A config gap worth naming now, not discovering cold later

configs/ppo.yaml never sets a gae_lambda key. The real plan as written therefore silently accepts sb3-contrib's library default, λ = 0.95 — the value used in the worked example above. This is worth stating explicitly here: it's a real hyperparameter choice being made by omission, and page 10 flags it again as something to name in the write-up rather than leave implicit.

Markov Decision Processes

The formal object that gives the agent–environment loop precise mathematical meaning — the language Phase 1 is written in.

The formal tuple

An MDP is defined by five things, usually written as the tuple (S, A, P, R, γ):

  • S — the state space. The set of all possible situations the agent could be in.
  • A — the action space. The set of all choices available to the agent (sometimes state-dependent, via a mask — more below).
  • P — the transition function. P(s' | s, a) — the probability of ending up in state s' given you were in state s and took action a. Encodes "how the world works."
  • R — the reward function. The scalar reward received for a transition, often written R(s, a, s').
  • γ (gamma) — the discount factor, a number in [0, 1] controlling how much the agent should value future reward relative to immediate reward.
Generic example

A robot navigating a grid. States are grid cells, actions are {up, down, left, right}, P says moving "up" succeeds 90% of the time and slips sideways 10% of the time, R is −1 per step (encouraging speed) with a bonus at the goal cell.

This project

S is the set of all possible 16-dimensional observation vectors; A is the 6 pit choices; P is compute_lap_time plus the tyre-age and weather-trace bookkeeping in step() — stochastic, since lap time includes Gaussian noise and weather/safety-car draws are random; R is -lap_time (or the terminal −500 penalty); γ = 1.0, chosen deliberately (below). Every one of these five objects has a literal, named counterpart in dynamics.py or f1_strategy_env.py — that correspondence is exactly what "Phase 1 defines the MDP" means in practice.

The Markov property

The "Markov" in MDP refers to the Markov property: the future depends only on the current state, not on the history of how you got there. Formally, P(s'|s, a) must not need to know anything about states before s. This is a design requirement, not something automatically true — if it doesn't hold, the state representation is incomplete.

This project

This is precisely why Phase 1 derives tyre_age and the out-lap warmup penalty the way it does, and explicitly rejects tracking a second, separate laps_since_pit counter: tyre_age alone already determines warmup (tyre_age == 1 means out-lap), so adding a second variable would be redundant — and worse, redundant variables that can drift out of sync are a way for hidden, un-observed history to sneak back into the transition function without you noticing.

Policies

A policy, written π, is the agent's strategy: a mapping from states to actions (deterministic) or to a probability distribution over actions (stochastic). "Solving" an MDP means finding the policy that gets the most total reward. Nothing about the policy lives in Phase 1 — Phase 1 builds the world the policy acts in — but every later phase (baseline heuristics in Phase 3, learned Q-tables in Phase 4, neural networks in Phase 5) is a different way of representing and improving a policy for this exact MDP.

Return and the discount factor

The return is the actual quantity an agent tries to maximize: the (possibly discounted) sum of all future rewards from a given point onward:

G_t = R_(t+1) + γ·R_(t+2) + γ²·R_(t+3) + γ³·R_(t+4) + ...

γ controls the trade-off between immediate and future reward. γ = 0 makes the agent totally short-sighted; γ close to 1 makes it weigh distant future rewards almost as much as immediate ones. γ strictly less than 1 is also what keeps the return finite in a continuing (never-ending) task.

This project

Phase 1 uses γ = 1.0 exactly, which looks mathematically dangerous (an unbounded sum) and isn't. Episodes are fixed-length (every race is exactly total_laps laps), so the return sum is always finite no matter what γ is. Given that, γ = 1 is not just safe but correct: with γ = 1, the return is Σ(-lap_time) over the whole race with every lap weighted equally — exactly -total_race_time. Any γ < 1 would instead make later laps count for less than earlier ones, biasing the agent toward good early-race pace at the expense of the finish, with no basis in what a race actually rewards. This is the reasoning behind the plan's comment "γ = 1.0 (fixed-length episodes; avoids late-race pace bias)."

Action masking

Real MDPs are sometimes written with a fixed action space for every state, with invalid actions made unattractive (e.g. reward -∞) so the agent learns to avoid them on its own. When it's known in advance which actions are invalid — as it is here — it's faster and more reliable to remove them directly. This is action masking: alongside each state, a boolean vector saying which actions are currently legal.

This project

The action mask enforces exactly the kind of hard constraints real racing regulations impose: intermediate tyres are illegal in the dry, slicks are illegal in the wet, you can't "pit" for the compound you're already on, and the two-dry-compound rule forces a pit stop once it's the only way left to satisfy it. Because both the environment and the Phase 3.5 dynamic-programming oracle must agree on exactly which actions are legal, the plan implements masking as a single shared free function (compute_action_mask in dynamics.py) that both consumers call — one place the rule can be gotten wrong, not two places that could silently disagree.

Worked example: one lap, two possible actions

Take a concrete state s and push it through P and R by hand, using illustrative but realistic constants of the shape calibration.json actually holds. This is exactly the arithmetic compute_lap_time performs — nothing here is simplified away.

State s: lap 30 of 52, fitted compound MEDIUM, tyre age 14 laps, DRY, no safety car, only MEDIUM used so far.

Constants used (illustrative):

base_pace92.000 s
compound_pace_offset[MEDIUM]0.000 s (reference compound)
compound_pace_offset[HARD]+0.550 s
MEDIUM: base_deg / cliff_age0.030 s/lap / 18 laps
fuel: consumption / sensitivity1.600 kg/lap / 0.033 s/kg
weather_compound_penalty[DRY][MEDIUM]0.000 s (matched tyre)
pit_loss (GREEN)22.000 s

Action A: STAY_OUT

Tyre age 14 is below MEDIUM's cliff_age of 18, so degradation is still in its linear phase: 0.030 × 14 = 0.420 s. With 22 laps remaining, fuel load contributes (22 × 1.600) × 0.033 = 1.162 s. Weather penalty and warmup are both zero (matched compound, tyre long past its out-lap). Called with rng=None — the exact-expectation form the DP oracle relies on — noise is omitted entirely:

lap_time = 92.000 + 0.000 + 0.420 + 1.162 + 0.000 + 0.000 = 93.582 s reward = −93.582

The next state s': lap 31, same compound, tyre_age = 15, one lap closer to the end.

Action B: PIT_HARD

The pit-lap ordering rule from the plan applies here: this lap is still run on the old tyre — MEDIUM at age 14 — so the base lap time is identical, 93.582 s. A pit-lane loss is added on top, undiscounted because there's no safety car active:

lap_time = 93.582 + pit_loss(GREEN) = 93.582 + 22.000 = 115.582 s reward = −115.582

The next state s': lap 31, compound now HARD, tyre_age = 1 (next lap is the out-lap, so its warmup penalty will apply then, not now) — and compounds_used now contains both MEDIUM and HARD, satisfying the two-compound rule for the rest of the race.

Comparing the two rewards, −93.582 vs. −115.582, is precisely the trade-off the agent must learn to weigh: pitting costs about 22 seconds right now, in exchange for fresher tyres and — critically, per the Bellman equation on page 3 — a better expected outcome over every lap that follows. A single-step comparison always favours STAY_OUT; the whole reason this is a sequential decision problem, and not a greedy one, is that the right comparison is between the two full returns, not the two immediate rewards.

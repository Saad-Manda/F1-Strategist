Annotated Code Walkthrough

src/evaluation/dp_oracle.py, src/env/weather_markov.py, and scripts/run_dp_oracle.py, read by dependency order: state enumeration first, then the recursion itself, then the two things that wrap it for evaluation.

This page does not reproduce the real code — by now you've built an equivalent structure yourself across page 5's five stages, and every piece named below should map onto something you already wrote in your own words. Treat it as labels for a shape you already know.

src/evaluation/dp_oracle.py

Reading order within the file, and what each piece is for:

  • DPState — the frozen dataclass from page 6. Indexed into a flat NumPy array via strides rather than kept as a dict of tuples (page 5's toy dicts were fine at a few hundred states; 363,000 states need the flat-array layout to stay fast). np.full(n_states, -np.inf, dtype=np.float64) is the whole value table, one array.
  • The reachability pass — a forward sweep from the race's actual start state, run once before solving, marking which of the 363,000 candidate states can ever actually occur (tyre_age <= lap, a fitted compound implies a bit in used_mask, and so on). This is page 6's 5–10× pruning number, made concrete: the backward pass below only ever touches states this sweep marked reachable.
  • The backward-induction loop — structurally identical to page 5's stage-4 solver: V[T+1, ·] = 0 (plus the two-compound terminal penalty where the rule is unmet, mirroring stage 3's mandatory-service rule), then for each lap from T down to 1, for each reachable state, for each action the (shared) mask permits, compute cost + E[V(s')] and keep the minimum. γ = 1.0, matching the environment — the same justification page 6's Phase 1 prerequisite page gave for the live environment applies unchanged here.
  • The expected-immediate-cost step — calls dynamics.compute_lap_time(..., rng=None) and dynamics.compute_pit_loss(...) directly, never a reimplementation. Page 3's zero-noise argument is why this call is exact rather than an approximation; page 6's "why one shared implementation matters" section is why it has to be this exact function, not an equivalent-looking one.
  • Action validity — imported from dynamics.compute_action_mask, the same function F1StrategyEnv.action_masks() calls. Never restated locally — page 6 explains why a second, independently-written mask would be close to invisible as a bug.
  • DPOraclePolicy — wraps the solved table behind act(obs, action_mask) -> int, the same interface every other agent implements, so evaluate.py's paired-seed harness (Phase 3) runs it with no special-casing.

src/env/weather_markov.py

  • Fitting — page 4's counting-and-normalizing procedure, applied per circuit to every historical weather template Phase 0.5 extracted for that circuit: tally observed regime-to-regime transitions, divide each row by its total. The zero-row fallback page 4 mentioned (uniform row when a state was never observed as a starting point) is handled here, not left to crash on a division by zero.
  • Fit-quality reporting — per-transition counts and a held-out log-likelihood, alongside the fitted matrix. This exists so a thin data sample for a given circuit is visible and reported honestly, rather than silently producing a confident-looking matrix from too little evidence (page 4's closing note).
  • Sampling — page 4's cumulative-draw procedure, used both by Oracle B's expectation step and by F1StrategyEnv itself when weather_mode="markov", so the environment and the oracle draw from the identical fitted chain.

scripts/run_dp_oracle.py

The driver: solve every circuit (both oracle modes), cache each solved policy to data/processed/{circuit}/dp_policy.npz, and report the per-circuit solve time against the plan's under-10-seconds target. Re-run whenever dynamics.py or the calibration changes underneath it — a stale cached policy solved against an older version of the physics is exactly the kind of silent drift page 6 warns about, just at the level of a cache file instead of a second implementation.

What the test suite is actually checking

Each test in tests/test_dp_oracle.py targets one specific way this phase could go wrong — reading it alongside the implementation is, in effect, a list of every failure mode this page has already walked through:

  • test_oracle_value_matches_rollout — page 6's V[s_0]-vs-rollout check, made concrete: agreement within a small multiple of the noise standard error over 500 episodes.
  • test_dp_action_mask_matches_env — for 1,000 sampled reachable states, the DP's mask equals env.action_masks() exactly. This is the automated version of page 5's stage-3 sanity habit.
  • test_oracle_no_absurd_exploit — page 5's stage-5 exercise, for real: the oracle's race time must land within 15% of the best hand-computed 1-stop plan. By some distance the highest-value test in the file — it's the thing that would have caught "the agent learned to pit every lap because a warmup penalty has the wrong sign" before three days get spent blaming a learning algorithm for a bug in the model it was faithfully optimizing against.
  • test_oracle_a_dominates_oracle_b — a correctness check on both oracles at once: perfect foresight can never be worse than the achievable version, by page 6's own definition of the two.
  • test_oracle_respects_two_compound_rule / test_oracle_pit_count_plausible — the mandatory-service constraint (page 5's stage 3, for real) actually binds, and the resulting strategy makes a plausible number of stops (1–3 on a dry circuit, never 0, never more than 4).

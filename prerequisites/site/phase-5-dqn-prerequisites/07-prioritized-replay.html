Prioritized Experience Replay

Pit stops decide the race and are about 3% of the data. Prioritized replay samples by how wrong the network was, then corrects for having done so.

Your call · a uniform batch

A real race is 52 laps with about 1.5 pit stops on average. Page 04's memory draws a batch of 64 transitions uniformly.

About how many pit-stop transitions does a batch hold?

Surprise as a sampling signal

The 62 or so other transitions in that batch look much alike: one more lap on slightly older tyres, which the network learns early. The two that carry the strategy are outvoted in every batch. Phase 4's TD error δ = target − Q(s, a) can be read as how surprised the network was. A small |δ| is a transition it already predicts; a large one is a transition it got badly wrong. Prioritized experience replay (PER) samples by |δ|:

p_i = |δ_i| + ε ε is tiny, so no priority is ever 0 P(i) = p_i^α / Σ_k p_k^α α sets how much priorities count

At α = 0 sampling is uniform again; at α = 1 it is in proportion to the error. The plan uses α = 0.6. With three routine laps at |δ| = 0.5 and one pit stop at 8.0:

Each routine lapThe pit stop
α = 0 (uniform)25.0%25.0%
α = 0.6 (the plan)12.1%63.8%
α = 15.3%84.2%

At α = 0.6 the pit stop is drawn about 5.3 times as often as a routine lap (8.0^0.6 / 0.5^0.6 = 3.482 / 0.660), not 16 times. The exponent softens the ratio on purpose: a priority is only refreshed when its transition is drawn, so sampling by error alone would starve transitions that went stale, and training on the same few would fit those and forget the rest. A new transition has no δ yet, so it is stored at the largest priority in the memory, to be drawn at least once soon.

The correction: importance-sampling weights

Sampling by priority changes the world the network fits: if pit stops are 3% of experience and 15% of batches, it fits a race with five times as many pit stops. Each sampled transition's loss is scaled down by how over-represented it was, w_i = (N·P(i))^(−β), then divided by the batch's largest weight so weights only ever shrink a loss. In the four-transition example at α = 0.6, the pit stop's weight is 0.514 at β = 0.4 and 0.189 at β = 1. At β = 1 the correction is complete: drawn 5.3 times as often, each draw counting 0.189, and 5.3 × 0.189 = 1.0. The plan starts β at 0.4 and raises it toward 1 over training, accepting some distortion early, when every estimate is poor, and removing it late.

Each update samples a batch by priority, computes each transition's δ in the loss, multiplies each loss by its weight, then writes the new |δ| back as the priority. Once a pit stop is learned, its |δ| falls and it is drawn less.

Deep diveThe sum tree: sampling by priority in 17 steps280 words

Sampling in proportion to priority from 100,000 transitions by adding up priorities from the start costs up to 100,000 additions per draw. A sum tree does a draw or an update in about 17 steps, the depth of a binary tree with 100,000 leaves. Each leaf holds one transition's p^α and each node the sum of its two children, so the root holds the total:

[10] / \ [4] [6] / \ / \ [3] [1] [4] [2] leaf0 leaf1 leaf2 leaf3

A draw. Pick a number between 0 and the total, say 6.5. At each node go left if the number is no larger than the left child; otherwise subtract the left child and go right. At the root, 6.5 > 4, so 6.5 − 4 = 2.5 and right; at [6], 2.5 ≤ 4, so left: leaf2. Leaf2 owns the stretch from 4 to 8 of 10, so it is reached 4 times in 10.

An update. Change leaf1 from 1 to 5, a change of +4, and add it on the path to the root: the parent 4 → 8, the root 10 → 14. The real buffer stores the tree in one flat array, the root at index 0 and the children of node k at 2k+1 and 2k+2, leaves in the last capacity slots, which is why its code adds or subtracts capacity − 1. It draws a batch by cutting the total into one equal segment per slot and drawing once from each.

A bug recorded against the real plan

The leaves hold p^α, not p. The plan's add() reads the largest leaf as "the current maximum priority" and raises it to α a second time before storing it. With a largest leaf of 3.482, a new transition should be stored at 3.482; the buggy version stores 3.482^0.6 = 2.114, about 40% too low. Page 09's report shows a fault like this leaves the race unchanged; only a test that reads the memory catches it.

Prioritized replay in the case

Prioritized replay decides what training sees, and its recorded bug changes which transitions are drawn. Neither does anything once training stops, and the champion was trained with a uniform memory in any case. A memory fault could leave a wrong number in the network, which would show in every race, as on page 06.

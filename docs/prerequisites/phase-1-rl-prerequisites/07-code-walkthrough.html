dynamics.py and f1_strategy_env.py, read by dependency order rather than top to bottom: pure functions first, then the class that composes them.

This page does not reproduce any of that code — by this point you've already built an equivalent structure yourself in page 5's toy stages, and every function named below should map onto a stage you already wrote in your own words. Treat this page as a set of labels for a shape you already know, not as a substitute for opening the real files.

dynamics.py — pure functions only, and why

Every function in this file takes its inputs explicitly (compound, tyre_age, params, ...) and returns a value with no side effects and no reference to any class state. This is a deliberate constraint, not an accident of style: three different consumers — the live environment, human-written baseline strategies, and the Phase 3.5 dynamic-programming oracle — all need to call the same physics with different inputs at different times. A pure function is trivially safe to share: call it with the same arguments from anywhere, get the same answer, no hidden state to keep synchronized. A method on a stateful class would tie the physics to one particular environment instance, making it awkward or unsafe for the DP oracle — which needs to evaluate lap times for hypothetical states the live environment was never actually in — to reuse.

Reading order within the file, and what each function is for:

  • compound_pace_offset — the fixed, compound-level pace difference. What makes compound choice a real decision rather than noise.
  • tyre_degradation — piecewise: linear up to cliff_age, then a capped quadratic beyond it. The cap (cliff_cap) is as important as the cliff shape — an earlier, uncapped version let one very old tyre's degradation swamp every other signal in the reward.
  • out_lap_warmup — derived entirely from tyre_age (no second counter), decaying from full penalty at tyre_age == 1 to zero by tyre_age == 3.
  • fuel_effect — linear in laps_remaining; the car gets faster as the race burns fuel.
  • weather_compound_penalty — a lookup table keyed by (weather, compound): the physical cost of running the wrong tyre for the conditions.
  • compute_lap_time — composes all of the above, with an explicit branch for safety car / VSC laps and an rng parameter that, when None, returns the exact expected lap time rather than a sampled one — required by the DP oracle.
  • compute_pit_loss — the time cost of a pit stop, discounted under SC/VSC because the whole field is circulating slowly anyway.
  • compute_action_mask — the five-rule mask from page 6, as one shared function.

f1_strategy_env.py — the stateful Gymnasium wrapper

The class holds exactly the state a race actually has — current lap, fitted compound, tyre age, which compounds have been used, the sampled weather scenario and safety-car trace for this episode — and every method is a thin layer that reads that state, calls into dynamics.py for any actual physics, and writes the result back.

  • __init__ — loads calibration.json, builds observation_space (Box(16,)) and action_space (Discrete(6)). No episode state is created here — that's reset()'s job.
  • reset() — samples a new weather scenario and safety-car trace independently, sets tyre_age = 1 for the starting tyre (lap 1 is the out-lap — cars start on tyres fitted on the grid), and honours options={"starting_compound": ...} and the curriculum hook.
  • step() — the order-of-operations rule from page 6 lives here: compute this lap's time on the current (old) tyre first, add pit loss if pitting, then switch the fitted compound and reset tyre_age to 0.
  • _get_obs() — assembles the 16-dim vector from current state, and asserts both the shape and the [0, 1] bounds every single call, not just in tests — a cheap habit that catches a normalization bug the moment it's introduced.
  • action_masks() — delegates to dynamics.compute_action_mask; deliberately does not reimplement any rule locally.
  • _get_info() — returns the public contract dictionary. info.get(...) in Python returns None rather than raising when a key is missing, so a renamed key breaks every downstream phase silently, with no exception to point at the bug. Adding new keys is always safe; renaming or removing one is a breaking change.

What "≥10 tests" in test_env.py are actually checking

The test list in the plan isn't an arbitrary coverage quota — each test targets one specific way the implementation could plausibly go wrong, most tied directly to a design decision covered on this page or page 6:

  • test_return_equals_negative_race_time — the core identity from page 3 (return = −total race time) actually holds in code, not just on paper.
  • test_pit_lap_runs_on_old_tyre — the pit-lap ordering rule above wasn't silently inverted.
  • test_sc_timing_is_not_memorizable — safety cars are genuinely re-sampled per episode, not accidentally replayed (page 1's reward-hacking concern).
  • test_cliff_is_capped — the degradation cap actually caps, rather than only capping the quadratic term while some other path still lets values blow up.
  • test_action_mask_forces_pit_near_end / test_two_compound_rule_violation_penalty — the mask and the backstop penalty each do their half of the two-compound rule correctly.

Reading the test file alongside the implementation file is, in effect, reading a list of "here is every way an earlier draft of this plan was found to be wrong" — worth treating as required reading, not optional verification.

Why this matters

A controller needs a representation that lets it predict the consequences of its decisions. It does not necessarily need to predict the exact outcome of a random event. It does need the right distribution of possible outcomes without having to consult an omitted part of the past.

The Markov property says the present state and chosen action are sufficient for that next-step distribution. Older history adds no predictive information once the state is known. This is a claim about the chosen representation and model, not a promise that the world is deterministic.

Compare two histories

In the switch world, history A starts in mode 0 and immediately chooses CLAIM. History B starts in mode 0, chooses FLIP, then CLAIM. The broken observation is 0 before either CLAIM, yet A gets −1 and B gets +1. Remembering the preceding FLIP changes our prediction. The observation by itself therefore fails this sufficiency test.

Now report the mode instead. Given mode 0 and CLAIM, the reward is −1 and the task ends. Given mode 1 and CLAIM, the reward is +1 and the task ends. Given either mode and FLIP, the next mode is one minus the current mode, reward is 0, and the task continues. No earlier action is needed to compute these outcomes.

def switch_step(mode, action):
    if action == "FLIP":
        return 1 - mode, 0, False
    if action == "CLAIM":
        return mode, (1 if mode == 1 else -1), True
    raise ValueError("unknown action")

In a stochastic variant, FLIP might succeed four times out of five. Mode and action can still specify that distribution. Randomness is compatible with a Markov state; omitted predictive information is the issue.

Read the formal statement

Write S_t for the state before transition t, A_t for the action, and r_t for its reward. The subscript t is an index, beginning at 0; t+1 means the following state. The letter P here means probability, and the vertical bar means “given.”

P(S_(t+1), r_t | S_t, A_t, earlier history) = P(S_(t+1), r_t | S_t, A_t)

This equality says that conditioning on extra history does not change the prediction when the state is sufficient. It covers both the next state and reward. A representation that predicts movement but hides a reward-relevant variable is still incomplete.

Time can be part of state

Suppose a modified task allows at most two decisions and an unclaimed parcel expires afterward. Mode 0 with two decisions remaining differs from mode 0 with one remaining: there may be time to FLIP then CLAIM in the first situation, but not the second. Use a state such as (mode, remaining). The countdown is part of this task, so expiry is termination.

An outside collector stopping after two calls does not introduce expiry into the switch's task rules. That is truncation, as in lesson 1.1. Do not add “steps until this training batch fills” to the task state just to disguise an arbitrary batch boundary.

Common mistake: assuming that including the current observation automatically makes an environment Markov. Sufficiency depends on the dynamics, rewards and task horizon.

Must a sufficient switch state contain every previous FLIP?

No. Current mode summarizes the effect of those actions. For an intrinsic deadline, add remaining decisions; the entire action log is unnecessary.

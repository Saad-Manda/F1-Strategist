Phase 1 RL Prerequisites

Everything — and only what — you need to read and build phase-1-gym-environment.md with no prior reinforcement-learning background. No later-phase material.

Why this project is an RL problem at all

An F1 race strategist makes a sequence of decisions — stay out, or pit for a given tyre — under uncertainty (weather, safety cars, rivals) with a single, measurable goal: minimize total race time. That is exactly the shape of problem reinforcement learning is built for: an agent that repeatedly observes a state, picks an action, and receives a reward, with the goal of maximizing total reward over time. Supervised learning has no answer to "what should I do next, given that today's action changes tomorrow's options" — that sequential, consequence-carrying structure is what makes this an RL problem and not a classification problem.

This exists because Phase 1 is "the intellectual heart of the project" — it defines the simulator every future agent trains inside. A mistake here (a wrong reward, a leaky observation, a masking bug) silently corrupts every phase that follows.

Scope, precisely

Phase 1 builds an environment. It does not train an agent — no Q-learning, no neural networks, no policies. So this doc set teaches exactly two things in depth: the math that defines what an environment is (an MDP), and the software contract (Gymnasium) that f1_strategy_env.py must implement. Everything below is in service of one or the other. Algorithm training (Phases 4, 5, 9) is a different set of prerequisites for a different day — nothing about it is covered here, even in preview.

How this folder teaches the implementation half

Nowhere in pages 1–7 is the real project's code reproduced. Instead, page 5 has you build a sequence of small, runnable toy environments under your own names, each adding one real-world complication a plain toy ignores — multiple tyre compounds, a capped wear cliff, fuel burn-off, weather mismatch, correctly-ordered pit stops, a randomly-sampled safety car, action masking, reward centring — until the toy's shape converges on what the real environment needs, without ever looking like the real environment's actual code. Only after that does page 6 name which piece of the real dynamics.py and f1_strategy_env.py corresponds to which toy stage — grounding, not transcription.

How to use this alongside the Phase 1 plan

Read pages 1–4 once, in order, treating the F1 examples inside them as illustrations only. Page 5 is hands-on: build the toy environments yourself, in your own words and your own code, adding one complication at a time — that's what makes the ideas stick, rather than reading someone else's finished file. Page 6 then re-derives the same concepts using nothing but this project's actual design decisions — at that point the abstractions from pages 1–4 should stop feeling abstract, and page 5's toys should feel like recognisable sketches of it. Page 7 is the closest thing to a line-by-line reading guide for the plan itself. Keep page 8 open as a reference while you work.

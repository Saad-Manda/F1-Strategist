Page 06 / 08 — Grounding

This Project, Formalized as a DP

Pages 1–5, inverted: every formal object from the recursion, matched to exactly what it is in dp_oracle.py's actual design.

The DP state

Where Phase 1's environment observation was a flat 16-dimensional vector, the DP oracle's internal state is a small, explicit tuple — it needs to be hashable and enumerable, not shaped for a neural net:

@dataclass(frozen=True)
class DPState:
    lap: int              # 1..total_laps
    compound: int          # 0..4  (SOFT/MEDIUM/HARD/INTER/WET)
    tyre_age: int          # 1..total_laps
    used_mask: int          # 0..7 -- bits for SOFT/MEDIUM/HARD
    sc_active: int          # 0 or 1
    weather: int           # 0..2  -- Oracle B only; fixed per lap in Oracle A

Every field maps directly onto something pages 2–5 already built a version of:

FieldToy-solver equivalent
lapThe backward-pass index t in every stage of page 5
tyre_ageage, stage 1 onward
sc_activesc, stage 2 onward
weatherw, stage 4
compound, used_maskNot built in the toy — the real state's compound-choice dimension, masked by compute_action_mask exactly as stage 3's has_pitted masked STAY

The state-space size, arithmetic in full

Page 1 quoted the headline number; here's where each factor comes from:

lap ≈ 55 (total_laps, circuit-dependent) compound = 5 (SOFT / MEDIUM / HARD / INTER / WET) tyre_age ≈ 55 (capped at total_laps) used_mask = 8 (2³ -- three dry compounds, each used or not) sc_active = 2 weather = 3 (DRY / DAMP / WET) ------------------------------------------- 55 × 5 × 55 × 8 × 2 × 3 ≈ 363,000 states, × 6 actions

Backward induction over that, in NumPy, runs in well under a second per circuit — the plan's stated definition-of-done target is under 10 seconds. Most of the 363,000 are unreachable — tyre_age can never exceed lap, and a fitted compound implies at least one bit of used_mask — so a reachability pass computed forward from the race's actual start state, before solving, typically prunes 5–10× of that off, the same discipline page 1 previewed and every stage of page 5's toy solver practiced by only ever iterating over ages that were actually possible at each lap.

Sign convention: the DP minimises cost, the agent maximises reward

Every recursion on pages 2 and 3 was written as a min over cost, matching dp_oracle.py directly. The live environment and every RL agent instead maximise reward = -lap_time. These are the same optimization — argmin(cost) = argmax(-cost) — related by a single sign flip applied once, at the boundary where the oracle's policy is wrapped for use by the shared evaluation harness (below), never scattered through the DP's internals. Keeping the DP itself entirely in cost terms, as pages 2 and 3 did throughout, is what makes it safe to reuse a well-tested minimization loop without re-deriving a maximization version of the same equations.

Oracle A vs. Oracle B, precisely

Page 4 introduced the distinction in general terms; here it is exactly as the plan specifies:

Oracle AOracle B
Weather handlingFixed to one specific historical trace; lap alone determines weather, known in advanceTracked in DPState.weather, transitions drawn from the fitted 3×3 matrix (page 4)
What it answers"Best possible time for a strategist who already knows this exact race's weather""Best possible time for a strategist who observes only the current regime, same as the agent"
Achievable by an RL agent?No — provably not, it's an upper bound on a harder questionYes, in principle — it's the optimal policy of the exact MDP the agent trains in
Gap to it decomposes asinformation gap + algorithmic gappure algorithmic gap — the honest number to report

Oracle A − Oracle B is the value of perfect foresight — how many seconds a strategist would save by genuinely knowing the weather in advance, versus only being able to reason about it probabilistically. It's reported per circuit as an interesting result in its own right, not folded into either agent's evaluation.

This project

F1StrategyEnv gains a weather_mode option ("template" or "markov") specifically so Oracle B's assumption — the agent faces a Markov weather process, not a replayed historical trace — is something the environment can actually be run under, not just something the oracle assumes in isolation. Templates stay the default for the dashboard and the historical-race counterfactual in Phase 7, because "this is the real 2023 Dutch GP's actual weather" is a better demo than a sampled chain; "markov" mode exists purely so Oracle B's target is one the agent can be trained and measured against on equal footing.

Worked example: one backward-induction cell, at the real state's scale

Take a state late in a 55-lap race — lap 50, on a 6-lap-old MEDIUM, DRY, safety car currently green, both dry compounds already used (so no mandatory-pit pressure) — and trace the STAY branch's cost exactly as pages 2 and 3 did, just with the real function names in place of the toy ones:

this_lap = dynamics.compute_lap_time(compound=MEDIUM, tyre_age=6, laps_remaining=6, weather=DRY, sc_active=False, rng=None) = (page 3's zero-noise expectation, exactly — not an approximation) expected_next = Σ_{sc'} Σ_{w'} P(sc' | sc_active=False) · P(w' | DRY) · V[lap=51, MEDIUM, age=7, mask, sc', w'] V[lap=50, MEDIUM, age=6, mask, sc=False, w=DRY] = min( this_lap + expected_next, # STAY this_lap + dynamics.compute_pit_loss(sc_active=False) + expected_next_after_pit # PIT_*, for each legal pit target )

Nothing here is new relative to page 5's stage-4 solver — the double sum over sc' and w' is precisely expect_both from that stage, and the min over legal actions is precisely stage 3's masked comparison. The only difference is scale: five real compounds instead of a toy's two or three, a real fitted 3×3 weather matrix instead of the page 4 illustration, and a genuine calibrated hazard instead of an invented 0.2. If any piece of this cell's structure feels unfamiliar, that's the signal to go back and build the missing piece as a toy on page 5 before reading dp_oracle.py itself.

The rollout harness and the optimality-gap metric

DPOraclePolicy wraps the solved (V, π*) tables behind the same act(obs, action_mask) interface every other agent uses, so evaluate.py's paired-seed harness (Phase 3's own evaluation methodology) runs it unmodified. Crucially, the oracle is scored by rolling it out in the real environment with noise switched back on — never by reading V[s_0] directly. V[s_0] is the expected cost under the model, computed exactly using page 3's zero-noise shortcut throughout; the rollout mean is the measured cost under the actual simulator, noise included. The two should agree within sampling error — test_oracle_value_matches_rollout checks exactly that, and a large divergence points at either a bug in the expectation math or a drift between the oracle's model and the live environment's.

Every results table from Phase 4 onward gains one column, defined here and used unchanged everywhere downstream:

optimality_gap(agent) = mean_race_time(agent) − mean_race_time(oracle_B)

reported in seconds, with a paired bootstrap confidence interval computed over the same shared seed set every other head-to-head comparison uses.

Why one shared implementation matters more here than in Phase 1

Page 7 of the Phase 1 prerequisites already made the case that dynamics.py being pure functions is what lets the environment, the baselines, and this oracle all call the same physics. It matters even more acutely here: a DP oracle computing optimal values against a transition function that has quietly drifted from what agents actually train against doesn't fail loudly — it produces numbers that look authoritative, get written into a results table, and are simply wrong. compute_action_mask is extracted as one function during Phase 1 specifically so both F1StrategyEnv.action_masks() and the DP import the identical logic rather than two implementations that could each look individually correct while silently disagreeing — test_dp_action_mask_matches_env exists to catch exactly that class of drift, on every commit.

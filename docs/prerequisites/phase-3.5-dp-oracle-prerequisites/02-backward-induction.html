Backward Induction

The last decision in a race is always the easiest one to get right — because nothing comes after it. Backward induction is just that observation, applied one lap at a time, from the end of the race to the start.

Starting from a Bellman equation you already have

Phase 1 page 3 derived the Bellman optimality equation from first principles, by peeling the first reward off the return:

Q*(s, a) = Σ_s' P(s'|s,a) · [ R(s,a,s') + γ · max_a' Q*(s', a') ]

That page noted the equation admits two very different uses: Q-learning nudges a table toward satisfying it approximately, from sampled experience. Dynamic programming — this page — solves it directly, because for this project the right-hand side is fully computable: P and R are dynamics.py, not a mystery to be inferred.

The obstacle to just "solving" this equation directly is that it's circular — Q*(s,a) on the left depends on Q*(s',a') for other states on the right, which in turn depend on further states, and so on. In the general, infinite-horizon case, breaking that circularity requires iterating the whole equation repeatedly until the values stop changing (value iteration — see the aside below). A race doesn't need that trick, because it has something most MDPs in a textbook don't: a hard, known ending.

The horizon breaks the circularity

A race is exactly T laps long. After lap T, there is no lap T+1 — nothing to be uncertain about, and nothing left to optimize. That single fact turns the equation from circular into a straight-line recursion, computable in one backward pass:

V_(T+1)(s) = 0 (terminal condition — nothing follows the last lap) for t = T down to 1: for every state s reachable at lap t: V_t(s) = min_a [ cost(s, a) + E_s'[ V_(t+1)(s') ] ] π*_t(s) = argmin_a [ ... ] (the action achieving that minimum)

(This project's reward is -lap_time, so the oracle works in cost — minimizing total lap time — rather than maximizing reward. The two are the same optimization with a sign flip; page 6 makes the convention explicit for the real code.)

Read it lap by lap: V_t(s), "the best possible total cost from lap t to the finish, starting in state s and playing optimally," is computable the instant V_(t+1) is fully known for every state — because every term on the right-hand side only refers to t+1, never back to t itself. Start at the last lap, where V_(T+1)=0 makes the recursion trivial to evaluate, and each earlier lap becomes solvable in turn, using only work already finished. By the time the pass reaches lap 1, V_1(s_0) is the exact optimal expected cost of the entire race from the start — computed without ever having simulated one.

Why this is dynamic programming, not just algebra

The name "dynamic programming" refers to two properties this recursion exploits. Optimal substructure: the optimal plan from lap t onward is built from the optimal plan from lap t+1 onward — you never have to reconsider a later decision once its value is known. Overlapping subproblems: many different paths through the race arrive at the same (lap, tyre_age, compound, ...) state, and V_t(s) is computed for that state exactly once, then reused by every path that reaches it — the table is the memoization. Skip the table and recompute from scratch for every path, and the same tractable problem becomes exponential.

Worked example: when does pitting actually pay off?

A tiny 4-lap toy race, one tyre, one decision each lap: STAY or PIT. Deterministic — no safety cars or weather yet, that's page 3's job. Lap time grows with tyre age; pitting resets age to 1 but costs a fixed penalty charged to the lap you pit on:

lap_time(age) = 10 + 3·(age − 1) (age is laps since this tyre was fitted, starting at 1) pit_loss = 6 cost(age, STAY) = lap_time(age), next age = age + 1 cost(age, PIT) = lap_time(age) + pit_loss, next age = 1 race starts lap 1 with age = 1 (fresh tyre from the grid)

Fill the value table backward, one lap at a time. Lap 4 (the last lap): with V_5 = 0, pitting only adds +6 for no benefit — the last lap never justifies a pit stop, because there is no lap 5 left to recoup the cost on. So π*_4 = STAY for every age, and V_4(age) = lap_time(age):

Reading the optimal policy back out

Walk forward through the π* table, always taking the action recorded for the state you're actually in: lap 1 age 1 → STAY (age becomes 2) → lap 2 age 2 → PIT (age resets to 1) → lap 3 age 1 → STAY (age becomes 2) → lap 4 age 2 → STAY (forced, last lap). Total cost: 10 + 19 + 10 + 13 = 52 — matching V_1(1) exactly, as it must. Compare that to the policy that never pits at all: 10 + 13 + 16 + 19 = 58. One well-timed pit stop, at exactly the right lap, saves 6 — and backward induction found both the fact that pitting helps and the single lap where it helps, purely by propagating values backward from a horizon of zero future laps to a horizon of four.

Why a one-step-ahead ("greedy") policy would have missed this

A policy that only compares this lap's immediate cost — ignoring V_(t+1) entirely — picks STAY at every single lap in this example, because STAY is cheaper than PIT on every lap taken in isolation (lap_time(age) < lap_time(age) + 6, always). That greedy policy is exactly the always-stay policy above, costing 58. The extra 6 backward induction is willing to spend at lap 2 only makes sense in light of what it buys three laps later — information a one-step-ahead view structurally cannot see. This is the general shape of the pitfall Phase 1's "common pitfalls" section warns about for a rising learning curve, arriving here in a much sharper form: the correct policy is provably not the myopic one.

Backward induction vs. value iteration — a note for the resource map

The plan's resource map points to Sutton & Barto chapter 4, which covers dynamic programming for the infinite-horizon, discounted case: value iteration repeatedly sweeps and updates V(s) for every state using the current estimate of V, and only converges to the true values in the limit, because with no fixed end there's no V_(T+1)=0 to anchor a single clean backward pass. Backward induction — what this page and the DP oracle actually use — is the finite-horizon special case: because a race has a hard, known length, the exact values are obtained in a single pass, lap by lap, with no iteration to convergence required. Chapter 4's ideas transfer directly; the finite horizon is what makes them exact here rather than merely convergent.

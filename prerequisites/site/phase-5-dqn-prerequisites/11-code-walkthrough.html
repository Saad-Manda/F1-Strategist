Reading order, and why it's this order

Read DuelingDQN.forward first. It is five lines, and the shape of its output is what everything else consumes. Then PrioritizedReplayBuffer, which stands alone and never touches a network. Then DuelingDoubleDQNAgent, which joins the two. Leave train_dqn.py for last, because it only makes sense once you know what each agent method does.

What to look for in DuelingDQN

  • The three nn.Sequential blocks are page 10's table: trunk, value_stream, advantage_stream.
  • The combining line is page 05's formula. Check the mean: it is taken over the last dimension, across actions, with keepdim=True. A mean over the batch dimension would run without error, and it would subtract the same six numbers from every row, which does nothing about identifiability.
  • Shapes. value has one column and advantage has six. Adding them relies on the single column being stretched across all six, which is the "shared across all actions" idea of page 05 carried out by the arithmetic.

What to look for in DuelingDoubleDQNAgent

  • The constructor builds two networks, copies the online weights into the target with load_state_dict, and gives the optimizer only the online network's parameters. That last detail is what "θ⁻ never receives a gradient" from page 03 looks like in code.
  • select_action is Phase 4 page 03's ε-greedy with a network in place of a table row: a random draw among legal actions, or an argmax after illegal actions are set to −inf. Notice there is no way to switch exploration off. That is page 10's evaluation issue.
  • update, the gate. The first lines return early unless the buffer has learning_starts transitions and _step is a multiple of train_freq. Note which method changes _step.
  • update, the target. Inside torch.no_grad() you should find, in order: the online network run on the next observations, illegal actions set to −inf, an argmax, the target network run on the same observations, a gather with the chosen indices, and the line reward + gamma * value * (1 − done). That is page 06's batch of three, with 64 rows. The no_grad block matters: the target is treated as a fixed number, and no gradient flows back through it.
  • update, the loss. smooth_l1_loss with reduction="none" gives one loss per row. Each is multiplied by its importance weight, and only then is the mean taken. Taking the mean first would leave nothing for the weights to act on. The gradient-clipping call sits between backward() and optimizer.step(), the only place it can have an effect.
  • update, the two write-backs. New priorities go to the buffer, then every target-network weight moves a fraction tau toward its online counterpart. This runs on every training step. The constructor also accepts target_update_freq, a hard-update setting from page 03, and never uses it. Only the soft update is implemented. It is an unused parameter and worth removing, not a bug.
  • save / load store both networks, the optimizer state, epsilon and the step counter. The replay buffer is not saved, so a run resumed from a checkpoint starts with an empty buffer and waits for learning_starts again.

The training loop

In train_dqn.py the order of calls inside the lap loop is the thing to read: select_action, env.step, read the next state's mask, store, update, decay_epsilon. The mask is read after stepping because it describes the state just arrived at, and that is the mask the stored transition needs. update is called every lap and decides for itself whether to do anything.

Each race logs its reward, mean loss, epsilon and pit count. Page 08 is the reason to watch more than reward. A flat reward with a falling loss and a flat reward with a flat loss are different situations. Pit count is the quickest check on behaviour: a policy that has collapsed to "never pit" or "pit every lap" shows there before it shows anywhere else.

One thing is promised and not delivered. The function's docstring lists "Q-value distributions (detect overestimation)" among its key logging, and the loop never logs a Q-value. The average Q-value is the one number page 08's table needs, and the one that would show page 06's overestimation. Add it when you build the file.

What each new test actually catches

TestWhat it defends againstWhat to notice
test_dqn_target_network_differs_from_onlineThe target network being the same object as the online network, or being overwritten with a full copy on every step. Either one silently turns the agent back into page 03's unstable naive version.As written, it stores 200 transitions and calls update(). The default learning_starts is 1,000, so update() returns without training and the two networks are still identical. The test fails for a reason that has nothing to do with what it is testing. It needs learning_starts set below 200. It also sets agent._step by hand to get past the gate, which is the counter coupling from page 10 showing up in a test.
test_per_samples_high_td_moreA buffer that stores priorities and then samples uniformly anyway.It passes explicit priorities to add(), so it never exercises the "new transition at maximum priority" path. The twice-applied exponent passes this test untouched.
test_action_masking_in_exploitationThe greedy branch of select_action choosing an illegal action.It covers action selection only. Nothing tests that the mask is applied inside update()'s target, which is the masking page 06 spent a section on.

Four tests would close the gaps this set has pointed at. Each takes a few lines:

  • After add() with no explicit priority, the new leaf equals the largest existing leaf.
  • A transition with terminated=True produces a target equal to its reward, whatever the networks output.
  • A transition whose next state has one legal action produces a target built from that action, even when the online network rates an illegal one higher.
  • In evaluation mode, two runs on the same seed produce identical races.

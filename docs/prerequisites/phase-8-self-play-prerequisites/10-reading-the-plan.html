Page 10 / 11 — Reading a plan critically

Reading the Implementation Plan's Code

Like Phase 6's equivalent page, this reads a plan's pseudocode, not a file that has actually been built and run — and, per page 06, this phase shouldn't be started at all until a different phase's file changes first.

Why this page is different

Phase 8 hasn't been implemented — there is no src/env/f1_pettingzoo_env.py or src/agents/self_play_trainer.py in the repository yet. What follows reads the pseudocode inside .antigravity/plans/phase-8-self-play.md itself. Per page 06, the single most important finding in this whole set doesn't even live in this phase's own files — it's a missing constraint one phase earlier, in Phase 6's dynamics — which is exactly why reading a plan critically, before implementation starts, matters here as much as it did for Phase 6.

Reading order

f1_pettingzoo_env.py's step() first — this is where the per-agent reward computation and _extend_obs live, a direct continuation of Phase 6's dynamics (assumed background), now wrapped per-agent rather than against fixed-script rivals. Confirm N_MULTI_OBS = 19 matches page 09's restatement, and that the gap/position feature computation is the same formula Phase 6 used, just recomputed against whichever agents are still active this episode.

Then self_play_trainer.py's CheckpointPool, matched directly against page 03 and page 05: confirm recency_bias = 0.7, max_pool_size = 50, and — the specific thing to check for, not assume — what pool.add(learner, episode=0) actually seeds the pool with before training starts. If it's still an untrained network relying on epsilon = 0.0 for "randomness," page 05's fix hasn't landed yet.

Then train_self_play's episode loop, where two efficiency issues live (distinct from Item I and the E4 dependency — these are performance problems, not correctness ones): a fresh F1PettingZooEnv is constructed inside the episode loop, meaning 20,000 constructions each re-read calibration.json and the whole scenarios.parquet from disk; and opponents are reloaded from disk via pool.sample() once per opponent per episode, rather than being cached by checkpoint path. Neither causes wrong results, but both make a 20,000-episode run far slower than it needs to be.

A specific pointer: where page 06's fix belongs

The blocking constraint (lap_time = max(own_lap_time, car_ahead_lap_time + dirty_air_penalty(gap))) belongs in F1MultiCarEnv's dynamics — Phase 6's file, not anything in either of Phase 8's own files. Don't look for it in f1_pettingzoo_env.py or self_play_trainer.py; per page 06, it's a precondition inherited from a different phase's codebase, restated here so the reader doesn't go looking for it in the wrong phase's code.

The payoff of this whole page

A checklist item can be perfectly well-specified — "undercut/overcut emergence visible in pit timing distribution" is a clear, checkable statement — and still be structurally unreachable for reasons the checklist itself never mentions. None of the plan's other listed checks would ever surface that; only reading the environment's own dynamics (Phase 6's, not Phase 8's) against what the metric is actually supposed to measure does. That's the same lesson Phase 6's own page 10 drew from its five original tests missing E4 entirely — carried forward here because it's the same kind of gap, one phase later.

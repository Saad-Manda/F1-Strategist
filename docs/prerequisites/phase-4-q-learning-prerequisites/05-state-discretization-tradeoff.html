State Discretization: The General Tradeoff

A Q-table is a dictionary. Dictionaries need hashable, finite keys. The 16-dimensional observation this project's environment hands out is neither — so something has to convert it into one first.

Why tabular methods need a finite table

Q(s, a) as used on pages 1–4 was written as if s were simply a label — s1, s2, and so on. In code, self.Q is a dictionary (or a defaultdict, page 8's choice) keyed by s directly, which means s has to be something a dictionary can use as a key: hashable, and drawn from a finite (or at least enumerable) set. The environment's real observation is a 16-dimensional float32 vector — normalized lap count, tire age, track temperature, and more, each one a continuous number. Two observations that are almost, but not quite, identical would hash to two different dictionary keys and never share a Q-value, which defeats the entire point of a table: generalizing across situations that are effectively the same.

Binning (equivalently, discretization) solves this by converting each continuous feature into a small number of discrete buckets — "tire age between 20 and 25 laps" instead of "tire age is exactly 22.7 laps" — so that nearby observations collapse onto the same table entry and a lookup table becomes possible at all.

The tradeoff, stated generally

Binning is a lossy compression of the state, and the compression ratio is a real design choice with real consequences in both directions:

  • Too few bins — genuinely different situations collapse into the same table entry. This isn't a training problem that more episodes or a better learning rate can fix: the agent literally cannot represent a different action for two situations sharing one bin, no matter how well trained the table is. Page 6 works through exactly this failure for the real plan's first-drafted binning scheme.
  • Too many bins — the table becomes too sparse to learn from in any reasonable number of episodes. Every cell needs to be visited many times before its Q-value estimate means anything (page 2's hand-run showed a single visit only moves an estimate a fraction of the way toward the truth); split the same amount of experience across ten times as many cells, and each cell gets roughly a tenth as many visits, most of which still won't be enough to say anything useful.

There's no bin count that dissolves this tension — only a choice of where along it to sit, informed by which of the two failure modes is more costly for the specific decision the table needs to make. This is precisely the tension the real plan's Definition of Done exists to catch, and precisely why Phase 5 exists at all: function approximation (a neural network standing in for the table) sidesteps the tradeoff entirely by generalizing across similar continuous states without needing to bucket them first — named here as the eventual resolution, not developed further; that's Phase 5's own prerequisites' job.

Worked arithmetic: how many states does a binning scheme actually produce?

The same kind of back-of-envelope arithmetic Phase 3.5 page 6 used to compute its 363,000-state DP enumeration applies here — with a different meaning. Phase 3.5's number was an exact enumeration: every state the DP oracle would ever need to solve for. This number is an approximation budget: how many distinct table entries a chosen binning scheme could ever produce, most of which won't be visited often (or at all) during a finite training run.

The real plan bins the 16-dim observation into eight discrete dimensions:

laps_remaining → 12 bins tire_compound → 5 bins (already discrete: SOFT, MEDIUM, HARD, INTER, WET) tire_age → 10 bins weather_regime → 3 bins (DRY, DAMP, WET) track_temp → 3 bins safety_car → 2 bins (active / not) compounds_used → 8 bins (2³ combinations of 3 dry compounds tried so far) mandatory_pit → 2 bins (yes / no) total states = 12 × 5 × 10 × 3 × 3 × 2 × 8 × 2 = 172,800
Discrepancy worth flagging before implementation

phase-4-q-learning-sarsa.md states this same product as 518,400, and its Risks table sizes the Q-table at "518,400 × 6 float64 ≈ 25 MB" on that basis. Multiplying the eight bin counts it lists, in any order, gives 172,800 — almost exactly a third of the stated figure (518,400 / 172,800 = 3), which suggests either an extra factor of 3 was meant somewhere in the binning scheme (a dimension with 3 bins was perhaps dropped from the list, or one bin count was mistyped) or the 518,400 figure itself is simply an arithmetic slip carried through the plan. Either way, this is worth resolving — by recounting the actual bins intended, not by picking whichever number looks more familiar — before discretize_obs is written, since page 6's "is memory actually the constraint" argument and any capacity planning depend on the real number. At 172,800 states the table is smaller still (172,800 × 6 × 8 bytes ≈ 7.9 MB), which only reinforces that memory was never the binding constraint on this scheme's coarseness.

Whichever total turns out correct, the shape of the exercise is the same one Phase 3.5 page 6 modeled: multiply the enumerated ranges of every state dimension together, and treat the result as a budget to be spent deliberately — coarse where a decision doesn't hinge on the distinction, fine where it does. Page 6 shows exactly what happens when one dimension of that budget is spent too coarsely.
